# 第四章 功能验证与性能评测

本章对第三章提出的 Tracing Map 地址预测方案进行功能验证与性能评测。首先介绍实验环境，包括处理器平台、仿真工具链和 FPGA 硬件平台（4.1 节）；随后通过多层次测试程序验证方案的功能正确性（4.2 节）；接着详细阐述性能评测方案，包括基准程序、SimPoint 采样方法论、硬件性能计数器基础设施、评测指标和对比配置（4.3 节）；最后分别对 SPEC CPU 2006 和 SPEC CPU 2017 两套基准程序的性能数据进行系统分析（4.4 节）。

## 4.1 实验环境

### 4.1.1 处理器平台与 SoC 框架

本文的实验基于 BOOM V3（SonicBOOM）处理器，采用 MediumBoom 配置（2-wide），运行于 Chipyard 1.13.0 SoC 设计框架之上。Chipyard 是由加州大学伯克利分校开发的开源 RISC-V SoC 集成开发框架，提供了从 RTL 设计到仿真验证再到 FPGA 原型验证的完整工具链。框架内集成了 Rocket 有序核心、BOOM 乱序核心、Gemmini 加速器等多种可组合的硬件模块，通过 Scala/Chisel 参数化配置系统实现灵活的 SoC 定制。

本实验的处理器配置名为 MediumBoomV3Config，其主要微架构参数如第三章表 3-1 所示，关键参数包括：2 宽度译码/分派/提交、64 条目 ROB、80 个整数物理寄存器、16 条目 LDQ/STQ、`memWidth = 1`（单 TLB/D-Cache 访问端口）以及 RV64GC 指令集支持。Tracing Map 方案的所有修改均在 BOOM 核心的 Chisel 源码中实现，通过 Chipyard 的构建流程生成 Verilog RTL，随后分别进入仿真环境和 FPGA 综合流程。

### 4.1.2 Verilator 周期精确仿真环境

功能验证和性能评测的主要手段是基于 Verilator 的周期精确仿真。Verilator 是一款开源的 Verilog/SystemVerilog 仿真器，其工作原理是将 RTL 设计编译为优化的 C++ 模型，相比传统的事件驱动仿真器（如 VCS、ModelSim），在纯功能验证和长程序仿真场景下具有显著的速度优势。

仿真流程如下：Chipyard 构建系统首先通过 FIRRTL 编译器将 Chisel 设计转换为 Verilog RTL，随后调用 Verilator 将 RTL 编译为 C++ 可执行的仿真二进制（simulator）。该仿真器加载 RISC-V ELF 格式的测试程序，在周期精确的模拟环境中执行，支持 `printf` 调试输出和波形（VCD/FST）生成。仿真过程中通过硬件性能计数器（HPM）采集 IPC、Tracing Map 命中率、微异常次数等性能指标。

Verilator 仿真环境的主要优势在于：（1）周期精确，仿真结果与真实硬件行为完全一致（在 RTL 层面）；（2）支持长程序仿真，可运行完整的 SPEC CPU 基准测试套件（数十亿条指令规模）；（3）便于插入调试逻辑和性能计数器，无需 FPGA 综合即可快速迭代设计。其主要局限是仿真速度较真实硬件慢数个数量级（典型速度约 10–100 kHz），长程序仿真耗时较长。

### 4.1.3 FPGA 硬件原型验证平台

为验证设计在真实硬件上的功能正确性和时序收敛性，本文还采用了 FPGA 硬件原型验证。FPGA 平台的硬件和软件环境如下：

**开发板。** 实验采用 Digilent Genesys2 开发板，搭载 Xilinx Kintex-7 系列 FPGA 芯片（XC7K325T-2FFG900C）。Kintex-7 325T 提供约 326K 逻辑单元、840 个 DSP48 Slice 和 16 MB Block RAM，具备承载 MediumBoom 配置（含 Tracing Map 扩展）完整 SoC 的资源容量。Genesys2 板载 1GB DDR3 SDRAM 作为主存，通过 MIG 控制器接入 SoC 的 TileLink 总线；此外提供 UART、SD 卡、以太网等外设接口，可支持操作系统级的软件运行。

**综合工具。** FPGA 综合与实现采用 Xilinx Vivado 设计套件。Chipyard 框架集成了 FPGA 构建流程（fpga-shells），可自动生成包含处理器核心、总线互连、存储控制器和外设控制器在内的完整 SoC 顶层设计，并调用 Vivado 完成综合（Synthesis）、布局布线（Place & Route）和比特流生成（Bitstream Generation）。生成的比特流通过 JTAG 接口下载到 FPGA 芯片中运行。

**运行方式。** FPGA 原型上的软件加载通过 SD 卡或 JTAG 完成。裸机程序（如 dhrystone、qsort）通过 RISC-V 代理内核（riscv-pk/bbl）引导执行；操作系统级验证则通过 OpenSBI + Linux 内核引导，经由 UART 串口交互。FPGA 原型的运行频率通常为 50–100 MHz，远低于 ASIC 目标频率，但可在秒级时间内完成 Verilator 仿真需要数小时的测试程序，是验证长程序正确性和调试硬件时序问题的重要补充手段。

## 4.2 功能正确性验证

在进行性能评测之前，必须首先确认 Tracing Map 方案的引入不会破坏处理器的功能正确性。功能验证的核心目标是证明：在所有测试场景下，修改后的处理器与基线 BOOM V3 产生完全一致的程序可见行为（寄存器状态、内存状态和 I/O 输出）。

### 4.2.1 验证策略

功能验证采用**分层递进**策略，从简单裸机程序到复杂系统软件逐步提升验证覆盖度：

1. **ISA 合规性测试**：运行 RISC-V 官方 ISA 测试套件（riscv-tests），覆盖 RV64GC 指令集的每条指令的基本功能，验证 Tracing Map 修改未破坏指令执行的正确性。
2. **裸机基准程序**：运行 dhrystone、qsort、median 等经典裸机基准程序，这些程序包含整数运算、排序算法、函数调用等典型计算模式，验证指令流在复杂控制流和数据依赖下的正确执行。
3. **代理内核引导**：通过 RISC-V 代理内核（riscv-pk）引导执行用户态程序，验证特权级切换、系统调用、虚拟内存管理等操作系统基础功能的正确性。riscv-pk 内部实现了页表管理、陷阱处理和系统调用代理，对处理器的特权态行为进行了较为全面的测试。
4. **操作系统级验证**：在 FPGA 平台上通过 OpenSBI 固件引导 Linux 内核启动，验证完整的多特权级切换、中断处理、虚拟内存和设备驱动等功能。Linux 内核的启动过程涉及数亿条指令的执行，是对处理器功能正确性最为严格的压力测试。

### 4.2.2 验证结果

**ISA 测试。** RISC-V 官方 ISA 测试套件中 RV64GC 相关的全部测试用例在 Verilator 仿真环境下均通过，测试结果与基线 BOOM V3 完全一致。这表明 Tracing Map 方案的引入未影响任何指令的执行语义。

**裸机基准程序。** dhrystone、qsort、median 等裸机基准程序在 Verilator 仿真和 FPGA 硬件平台上均成功运行，程序输出与基线版本完全一致。以 dhrystone 为例，程序完成标准迭代次数后输出的 DMIPS 得分和校验结果正确，确认了 Tracing Map 对 Load 执行路径的修改在整数运算密集型工作负载下不引入功能错误。qsort 测试覆盖了大量的指针操作和内存访问模式（数组随机读写、比较交换），对 Tracing Map 的地址预测和 SAB 的冲突检测形成了有效的功能压力。

**riscv-pk 引导。** 通过 riscv-pk 代理内核成功引导并执行了上述裸机程序以及额外的用户态测试程序。riscv-pk 在启动过程中执行页表建立、特权级切换（M-mode → S-mode → U-mode）和系统调用处理，所有流程均正常完成，无异常或陷阱错误。特别地，riscv-pk 的虚拟内存初始化过程涉及大量的 Store 和 Load 交织操作（页表项写入后立即读取验证），对 Tracing Map 的 Store-Load 冲突处理机制形成了严格的正确性检验。

**Linux 启动。** 在 FPGA 平台上，修改后的处理器成功通过 OpenSBI 固件引导 Linux 内核（基于 RISC-V 的 Buildroot 最小系统），完成内核初始化、设备树解析、根文件系统挂载，并进入 shell 交互环境。Linux 启动过程涉及数亿条指令的执行，包含密集的特权级切换、TLB 刷新、中断处理和 I/O 操作，是对处理器整体功能正确性最严格的端到端验证。

| 验证层次 | 测试内容 | 验证平台 | 结果 |

综上，本文方案在从单条指令到完整操作系统的各层次验证中均表现正确，未引入任何可观察的功能回归。这一结论为后续第 4.3 节的性能评测提供了可靠的正确性基础。

## 4.3 性能评测方案

### 4.3.1 基准测试程序

性能评测采用 SPEC CPU 2006 基准测试和 SPEC CPU 2017 基准测试[52]。SPEC CPU 2006 是由标准性能评估公司（SPEC）发布的行业标准处理器性能评测集，广泛用于学术研究和工业界的处理器微架构评估。该套件包含整数（CINT2006）和浮点（CFP2006）两个子集，覆盖了编译器、搜索算法、组合优化、视频编码、分子动力学模拟、流体力学计算等多样化的计算负载，能够全面评估处理器在不同访存模式和计算密集度下的性能表现。SPEC CPU 2017 是其后继版本，采用了更新、更复杂的工作负载，代码规模更大、数据集更新，能够更好地反映现代应用程序的访存特征。两套测试套件的联合使用增强了评测结果的统计可信度，覆盖了更广泛的计算场景。

本实验从 SPEC CPU 2006 和 SPEC CPU 2017 中各选取 10 个具有代表性的基准程序进行评测，共计20个。选取标准为：（1）能够在 RISC-V GNU 工具链[48]下成功进行交叉编译并通过功能验证；（2）覆盖整数和浮点两类工作负载，合计包含11个整数程序和9个浮点程序，分布较为均衡；（3）涵盖访存密集型和计算密集型两类不同特征；（4）两套测试集之间在应用领域上尽量减少重叠，以覆盖更广泛的计算场景。其中 gcc、lbm 和 omnetpp 在两套测试集中均有对应版本，本文将其纳入 SPEC CPU 2017 组进行评测。

### 4.3.2 SimPoint 采样方法

SPEC CPU基准程序规模庞大，单个程序的完整执行通常涉及数千亿条指令。在周期精确仿真环境及实际运行情况下，完整模拟一个程序可能需要数周乃至数月的时间，这在实际研究中是不可行的。

为解决这一问题，本文采用 SimPoint[49]采样方法论对基准程序进行代表性片段提取。SimPoint 的核心思想是：程序的动态执行行为在时间维度上会呈现出阶段性，表现为程序会在不同的执行阶段之间交替，每个阶段内部的微架构行为（如 IPC、缓存命中率、分支预测准确率等）较为稳定。SimPoint 通过以下步骤选取代表性片段：

1. 基本块向量（Basic Block Vector, BBV）分析：将程序的动态指令流按固定长度划分为若干区间，对每个区间统计基本块的执行频率，构成该区间的 BBV 特征向量。
2. 聚类分析：使用 K-means 等聚类算法对所有区间的 BBV 进行聚类，将行为相似的区间归为同一阶段。
3. 代表性区间选取：从每个聚类中选取距聚类中心最近的区间作为该阶段的代表性片段（SimPoint），并记录该聚类的权重（所含区间数占总区间数的比例）。

本实验中，每个基准程序选取权重最大的 SimPoint 片段进行仿真。每个 SimPoint 的仿真长度为12亿条指令，前10亿条指令作为预热阶段，用于填充缓存、分支预测器和Tracing Map等微架构状态，使其达到稳态；后2亿条指令为正式测量阶段，在此期间采集性能计数器数据。预热阶段的引入确保了测量结果不会受冷启动效应的影响。

SimPoint 方法论的有效性已在大量体系结构研究中得到验证：使用少数代表性片段即可以极小的仿真时间开销，获得与完整程序执行高度一致的性能特征。这使得在资源受限环境下对20个基准程序的全面评测成为可能。

### 4.3.3 硬件性能计数器

性能评测的数据采集依赖于在 BOOM V3 处理器上扩展实现的硬件性能计数器（Hardware Performance Monitor, HPM）。RISC-V规范中定义了标准的 CSR 性能计数器接口，但其可用计数器数量有限且缺乏灵活的采样控制机制。为满足本文方案评测中对细粒度微架构事件统计的需求，本文基于开源的 BOOM 性能计数器扩展框架BOOM-stop[50]进行了定制化实现。

除了常规的统计信息，本文对本方案相关的关键统计信息进行了扩展，包括Tracing Map快速地址转换命中次数、Tracing Map 更新次数、Tracing Map表项有效设置次数、立即数偏移更新次数、SAB冲突检测次数以及投机唤醒相关统计（总投机唤醒微操作数、重试路径投机唤醒微操作数、错误投机唤醒微操作数、重试路径错误投机唤醒微操作数）等。这些事件为深入剖析本方案的各子模块的行为特征提供了直接的硬件级观测手段。

该框架通过复用 RISC-V 指令系统的立即数加法指令实现对计数器的软件控制。处理器将这类指令识别为特殊的计数器操作命令，根据立即数的取值执行不同的控制功能，如计数器复位、计数器读取、计数器使能控制、统计权限级别等功能。这一控制机制完全在硬件层面实现，无需修改处理器的特权模式或中断处理逻辑，且对正常指令流的执行不产生任何性能开销。

基于上述基础设施，性能数据的采集流程如下：SimPoint 检查点加载后，测试程序首先通过控制指令设置进程标记、指令预热和统计权限级别。程序执行过程中，计数器在预热阶段结束时自动复位，随后在测量阶段内持续累加。测量阶段结束后，程序通过计数器读取指令依次读出所有计数器的值，并将结果输出至日志文件。分析脚本解析各基准程序的日志，计算 IPC等指标，并生成对比图表。

### 4.3.4 性能评测指标

本文采用以下指标评估本文方案的性能效果：

1）每周期指令数（Instructions Per Cycle，IPC）。IPC是衡量处理器执行效率的核心指标，定义为测量期间提交的指令总数与消耗的时钟周期总数之比。IPC 越高表示处理器在单位时间内完成的有效工作越多。对于超标量乱序处理器，IPC 综合反映了流水线利用率、缓存命中率、分支预测准确率等多种因素的共同效果。为了获得跨越多个基准程序的整体性能评估，本文采用几何平均值作为汇总指标。相比算术平均值，几何平均值对异常值更为稳定，且满足性能比值的一致性要求[51]。分别对 SPEC CPU 2006（10 个程序）、SPEC CPU 2017（10 个程序）和全部 20 个程序计算 IPC 几何平均值。

2）加速装入指令比例（Accelerated Load Ratio，ALR）。ALR衡量通过本文方案能加速的装入指令的覆盖程度。定义为Tracing Map命中且分发的装入指令和提交的装入指令数之比。

3）加速装入指令的推测式唤醒比例（Accelerated Load Speculative Wakeup Ratio，ALSWR）。该指标主要衡量加速的装入指令的进行推测式唤醒的出现次数。定义为加速装入指令的推测式唤醒次数与总推测式唤醒次数之比。

除了上述指标之外，还需要统计并分析内存序违例触发的微异常的变化情况、数据转换旁视缓冲器的未命中率变化情况、数据高速缓存未命中率变化情况等指标。这些指标的组合分析可以揭示不同基准程序下本文方案性能表现差异的底层原因。同时，还需要分析本文方案的成本开销。本文将根据综合工具报告，统计并分析方案的硬件资源使用量的情况。

而cactuBSSN_r（仅提升0.02%）的覆盖率在无ADDI时已达63.86%，说明其大部分装入指令的基址在循环间保持不变，无需偏移融合补偿；同时，cactuBSSN_r无论是否增加立即数偏移功能，Tracing Map的覆盖率都较高且几乎不变，说明该程序的访存模式以固定基址的非自增模式为主。

从Tracing Map表项更新次数的角度可以进一步揭示立即数偏移融合提升覆盖率的内在机制。在仅有基础Tracing Map的配置下，表项更新完全来自装入-存储部件的回写：当一条装入指令未命中Tracing Map时触发等待，待装入-存储部件完成地址计算后将基址回写，表项才变为有效。因此在基础配置下，每次循环迭代中基址寄存器被立即数加法修改后表项就会失效，下一次迭代的装入指令必须再次经过完整的访存流水线才能重新建立有效表项。这意味着表项在"有效—失效—等待回写—有效"的循环中反复切换，实际处于有效状态的时间窗口较短，能够被加速的装入指令比例因此受限。

启用立即数偏移融合后，立即数加法不再使表项失效，而是将偏移累积到缓存基址字段中，表项在循环步进过程中持续保持有效。这一变化的直接体现是：装入-存储部件的回写更新次数从平均每程序约1041万次下降至约825万次，降幅约20.8%——表项不再因立即数加法而频繁失效和重建，回写需求自然减少。与此同时，新增的立即数偏移更新平均每程序约894万次，表项的总更新次数从约1041万次增至约1718万次。总更新次数的增加恰恰说明了表项在更长的时间窗口内保持有效：在基础配置下这些立即数加法事件会使表项失效，而在偏移融合配置下则被转化为轻量级的偏移累积操作，表项在整个循环执行过程中持续可用。这正是覆盖率从27.29%提升至44.47%的根本原因。同时，立即数偏移更新仅涉及译码阶段的累加操作，硬件开销远低于需要完整访存流水线执行的装入-存储部件回写更新。

从各程序的特征来看，leslie3d的装入回写更新从1207万次大幅下降至485万次（降幅59.8%），而立即数偏移更新高达2568万次，说明该程序的大涡模拟计算中几乎所有基址寄存器的变化都是固定步长的立即数自增，偏移融合使得表项在大量迭代中持续有效，覆盖率因此从3.90%跃升至37.23%。lbm的变化最为极端：基础配置下仅有约29万次回写更新，启用偏移融合后立即数偏移更新达828万次（增幅2718%），对应的覆盖率从79.72%提升至95.34%，表项几乎在整个测量期间持续有效。相比之下，mcf_r的总更新变化仅为3.60%，立即数偏移更新仅381万次，反映了该程序以指针追踪为主的访存模式下立即数步进的出现频率较低，这也解释了其覆盖率提升较为有限（从5.42%提升至15.61%）。

在预测准确率方面，完整方案下所有20个基准程序的Tracing Map页面命中准确率均为100%，这验证了本文方案"预测必须正确"的设计约束——仅在确保虚拟地址位于同一缓存行时才进行快速转换，不引入任何错误预测。

Tracing Map将装入指令提前至分发阶段执行，可能增大与先序存储指令的地址冲突概率，导致存储-装入的内存序违例（在BOOM处理器中表现为mini exception）。通过对各种配置下的内存序违例次数进行统计，来分析出SAB冲突预检测效果。

从该数据分析可知，事实上Tracing Map对存储-装入的内存序异常的影响具有双向性。部分程序的微异常在引入Tracing Map后增加（如namd增加了72.33%，cactuBSSN_r增加了25.38%），正是因为绕过发射队列的装入指令提前执行后与尚未完成地址计算的存储指令发生了内存序上的冲突。另一部分程序的微异常反而减少（如astar减少了6.04%、perlbench_r减少了9.71%），这可能是因为绕过发射队列的装入指令更早完成后释放了装入-存储部件的资源，间接减少了因装入-存储部件的拥塞导致的冲突。

1）在最终方案中，重试路径是推测式唤醒的主要来源。重试路径平均贡献了68.17%的推测式唤醒次数，这意味着在完整方案中，超过六成的装入指令的推测式唤醒事件来自被加速的重试执行路径。部分程序的比例更高：lbm（99.99%）、leslie3d（94.66%）、h264ref（82.06%）、cactuBSSN_r（81.18%）和dealII（80.62%）的比例尤为突出，说明这些程序中绝大多数推测式唤醒事件都发生在Tracing Map加速的装入指令上。这一数据有力地证明了将推测式唤醒扩展到重试路径的必要性。若不进行此扩展，这些绕过发射队列装入指令的依赖指令将无法被提前调度，本文方案缩短装入指令延迟的收益也无法传递给依赖链下游。

2）重试路径的唤醒准确率优于正常路径。重试路径的平均失败率为43.00%，显著低于正常路径的70.80%。在20个程序中，18个程序的重试路径失败率低于正常路径（仅leela_r和lbm两个程序例外）。这一结果的可能原因在于：加速的装入指令一般有着较好的空间局部性（相同基地址寄存器），其数据高速缓存的命中率往往会高于通过正常流水线计算的装入指令，因此推测式唤醒的成功率更高。leela_r的两条路径失败率接近（30.86%对28.82%），而lbm由于其几乎全部的推测式唤醒都来自重试路径（99.99%），且其流式访存模式导致数据高速缓存缺失率较高（基线4.69%），使得两条路径的失败率均趋近100%。

3）整体推测式唤醒失败率分析。完整方案的整体推测式唤醒失败率平均为51.60%。这一比率虽然较高，但推测式唤醒的代价仅是被唤醒指令的重新调度，不涉及流水线回滚；而推测式唤醒成功时带来的依赖链延迟缩减收益是显著的。因此即使存在一定的失败率，推测式唤醒仍然是对IPC有净正收益的优化策略。由于重试路径的引入降低了加权平均失败率（从正常路径的70.80%拉低到整体的51.60%），推测式唤醒扩展实际上改善了整体唤醒质量。

在所有的基准程序中，blender_r的表现尤为突出：重试路径占比58.93%，但其失败率仅为19.10%，远低于正常路径的49.57%，说明Tracing Map为其3D渲染中的规则的数组访存提供了高质量的地址预测，使得依赖指令几乎可以确定性地被提前调度。相比之下，mcf_r虽然重试路径占比较高（57.01%），但其整体失败率也较高（58.22%），原因可能在于mcf_r的访存特性为数据高速缓存命中率低（基线缺失率6.37%），推测式唤醒失败的概率较大；但由于上文分析可知，推测式唤醒不涉及回滚，使得推测式唤醒的失败带来的额外损失较低，mcf_r仍然获得了+1.71%的IPC提升。perlbench_r的重试路径失败率仅36.98%，而正常路径高达83.77%，两者差距悬殊，进一步证实了Tracing Map预测地址对推测式唤醒准确性的提升作用。在SPEC CPU 2006中，namd（重试路径失败率31.09%对正常路径71.32%）和gobmk（32.97%对60.62%）也呈现出类似的差距，表明这一规律在不同测试套件之间具有一致性。

### 4.4.5 访存子系统影响分析

本文方案改变了装入指令的执行路径，使得装入指令访问存储子系统的顺序产生了变化，对数据转换旁视缓冲器和数据高速缓存均产生了间接影响。

**1）数据转换旁视缓冲器的影响。**

所有20个程序的数据转换旁视缓冲器的缺失次数均有所下降，这是本文方案的一个重要间接收益。一个可能的原因：加速的装入指令多来自循环体内对连续地址空间的访问，这些装入指令访问的虚拟页面高度集中。当这些高频装入指令提前进入装入-存储部件时，整个范围的装入指令减少了对数据转换旁视缓冲器表项的占用时间，使其有效容量得到释放，从而降低了整体缺失率。blender_r的缺失次数降幅最大（−25.62%），dealII次之（−23.21%），说明这两个程序的Tracing Map加速装入指令对数据转换旁视缓冲器压力缓解贡献最为突出。

尽管一级数据转换旁视缓冲器缺失率普遍下降，但部分程序的二级数据转换旁视缓冲器缺失次数出现了些许上升。可能的原因是：部分装入指令的延迟时间缩短，改变了程序原有的数据转换旁视缓冲器的访问时序。在基线配置中装入指令按照正常流水线顺序执行，数据转换旁视缓冲器访问在时间上可能较为分散；而在加速后，多条装入指令可能在更短的时间窗口内集中到达数据转换旁视缓冲器，当一级数据转换旁视缓冲器缺失后级联访问二级数据转换旁视缓冲器时，集中的访问压力可能导致二级数据转换旁视缓冲器中的页表项被更频繁地替换，从而增加了其未命中率。不过，二级数据转换旁视缓冲器缺失的绝对增幅较小（多数程序在1%至3%之间），总体上这一副作用不太会构成性能瓶颈。

**2）对数据高速缓存的影响。**

针对数据高速缓存主要有两方面的副作用，一种是由于访存顺序改变导致的数据高速缓存缺失的变化情况，另一种是由于访存顺序改变导致的数据高速缓存出现NACK次数的变化情况。

一级数据高速缓存的缺失率的波动幅度极小（绝对值变化均在0.2%以内），请求次数的变化也在1%以内（最终方案）波动且多数低于0.5%。这一结果说明本文方案对数据高速缓存的命中行为没有产生太多影响，数据高速缓存的命中或缺失模式保持稳定。

装入指令的延迟降低意味着更多的装入请求在较短的时间窗口内到达数据高速缓存，可能加剧端口竞争。从数据来看，20个程序中有17个程序的数据高速缓存的NACK次数有所增加，其中dealII（增加17.76%）、milc（增加6.55%）和omnetpp（增加5.88%）的增幅最为显著。但NACK增加并未完全抵消本文方案的收益，例如dealII仍然实现了6.93%的IPC提升，说明在多数情况下装入指令延迟缩减收益大于缓存竞争带来的损失。少数程序（如lbm）的NACK次数反而减少，这可能是因为延迟降低而提前完成了装入指令，错开了与其他访存请求的竞争窗口。

综合来看，本文方案对访存子系统的影响以正面为主：数据转换旁视缓冲器缺失率的显著降低是主要收益来源，数据高速缓存缺失率的稳定性表明本文方案没有对缓存层次结构造成负面干扰，数据高速缓存NACK的部分增加是可接受的副作用。

### 4.4.6 硬件资源开销分析

首先进行理论开销分析。Tracing Map方案中，主要新增了一个Tracing Map表。该表的表项包含1 bit的有效位、1 bit的等待位、6 bit的等待序号以及40bit基地址字段，一个条目的存储开销为48 bit。一共32个条目，故在该方案中寄存器的存储开销为1536 bit；立即数偏移融合功能由于复用了基地址字段，没有增加存储开销；SAB功能中一个条目内有效位占1bit、存储队列序号占4bit、移位寄存器的高位地址占38bit，一个条目占43 bit。在本设计中采用了4级的移位寄存器，且发射宽度为2，故存储开销为344 bit；推测式唤醒拓展不额外使用寄存器。总计新增寄存器为1880 bit，即235 Byte的寄存器开销。该开销不到 BOOM V3 MediumBoom 配置中整数寄存器堆容量（640 Byte）的37%，是轻量级的微架构扩展。

实际运行中，Vivado软件的资源利用报告给出了具体的硬件开销情况。这其中，LUT（Look-Up Table）资源可以视作逻辑的复杂度表现，FF（Flip-Flop）资源可以视作寄存器使用量的表现。经统计，基准BOOM V3处理器的LUT资源使用量为172275，FF资源使用量为95827；Tracing Map方案的LUT使用量为178082，FF资源使用量为98329；立即数偏移融合方案的LUT资源使用量为186583，FF资源使用量为98436；SAB方案的LUT资源使用量为188244，FF资源使用量为98819；最终方案的LUT资源使用量为189309，FF资源使用量为98856。

## 4.5 本章小结

本章从功能验证和性能评测两个维度对本文方案进行了系统性的实验评估。在功能验证方面，本文方案在 ISA 合规测试、裸机基准程序、riscv-pk 代理内核及 OpenSBI + Linux的完整操作系统启动等多层次测试中均表现正确，未引入任何功能回归。在性能评测方面，基于 FPGA上的实际运行结果和 SimPoint 采样方法论，对 SPEC CPU 2006 和 SPEC CPU 2017 各10个基准程序在五种递进的配置下的性能数据进行了全面分析。完整方案在20个程序上实现了2.85%的IPC几何平均提升，其中SPEC CPU 2006为3.63%，SPEC CPU 2017为2.08%。立即数偏移融合模块将Tracing Map的总体平均覆盖率从27.29%提升至44.47%。SAB 在冲突密集型程序中有效抑制了内存序异常并避免了性能回归。访存子系统分析表明数据转换旁视缓冲器缺失率普遍下降，数据高速缓存的缺失率保持稳定。硬件资源分析表明本文方案的资源开销在可接受范围内，未对处理器带来较大的硬件开销。
