# BOOM-stop：RISC-V BOOM 处理器硬件事件计数器与采样支持框架

## 1 背景与动机

### 1.1 RISC-V 标准性能计数器机制的局限性

RISC-V 指令系统规范定义了标准的硬件性能监控（Hardware Performance Monitor, HPM）接口，包括 Zicntr 扩展提供的三个基础计数器（`mcycle`、`mtime`、`minstret`）和 Zihpm 扩展提供的最多 29 个通用性能计数器（`mhpmcounter3` ~ `mhpmcounter31`），以及对应的事件选择寄存器（`mhpmevent3` ~ `mhpmevent31`）。尽管该标准接口为性能监控提供了基本的框架，但在实际的处理器微架构研究中存在以下局限性：

**1）计数器数量和事件定义受限。** RISC-V 规范仅定义了计数器的 CSR 编址方案，但并未标准化事件选择寄存器（`mhpmevent`）的字段含义。各处理器实现自行决定支持哪些事件及其编码方式。在 BOOM V3 的默认实现中，可用的性能事件数量较为有限，难以覆盖装入指令延迟分析所需的多维度微架构事件（如 D-TLB 访问/缺失、D-Cache NACK、装入/存储队列占用、推测式唤醒统计等）。

**2）缺乏灵活的软件控制机制。** 标准的 CSR 性能计数器需要通过 M 态或 S 态的特权指令（`csrr`/`csrw`）进行读写。在运行基准测试程序时，读写 CSR 计数器需要通过系统调用或特权态代码完成，这引入了额外的上下文切换开销，且软件控制流程较为复杂。

**3）缺少预热（Warmup）与采样控制。** 在基于 SimPoint 的性能评测方法论中，需要先执行一段预热阶段填充缓存和预测器状态，再进入正式测量阶段。标准 HPM 接口不提供基于指令数的自动预热复位、基于事件阈值的自动采样触发等高级功能，研究人员必须在测试程序中手动插入控制逻辑。

**4）缺少进程级隔离支持。** 在操作系统环境下运行基准测试时，标准计数器无法区分不同进程的事件贡献。操作系统调度、中断处理等内核态事件会污染用户态程序的性能数据，降低测量精度。

### 1.2 BOOM-stop 的设计目标

BOOM-stop 是一个面向 RISC-V BOOM 处理器的硬件事件计数器与采样支持框架。该框架通过在处理器硬件中增加额外的控制寄存器和事件计数器，并利用一种轻量级的指令编码复用机制实现对计数器的软件控制，旨在解决上述标准接口的局限性。其核心设计目标包括：

- **大规模事件覆盖**：支持 63 个硬件事件计数器，覆盖从取指、译码、分发、发射到访存子系统的全流水线微架构事件。
- **零开销软件控制**：通过复用 RISC-V 指令系统中的 `addi x0, x0, imm` 指令（该指令在标准语义下等价于 NOP）实现对计数器的设置、复位和读取，无需 CSR 访问或特权态切换。
- **内建预热与采样**：硬件层面支持基于指令数的自动预热复位和基于事件阈值的采样触发，与 SimPoint 方法论无缝集成。
- **进程级标记**：通过进程标识寄存器（`procTag`）支持进程级的事件计数隔离。

### 1.3 与其他性能监控方案的对比

| 特性 | RISC-V 标准 HPM | Linux perf（需 Sscofpmf） | BOOM-stop |
|------|----------------|--------------------------|-----------|
| 计数器数量 | 最多 29 个 | 受硬件限制 | 63 个 |
| 事件定义 | 实现自定义 | 依赖硬件事件映射 | 预定义 63 个全流水线事件 |
| 控制方式 | CSR 特权指令 | 系统调用 + 内核驱动 | 用户态 ADDI 指令 |
| 预热支持 | 无 | 需软件实现 | 硬件自动复位 |
| 采样触发 | 无（需 Sscofpmf 扩展） | 中断驱动 | 硬件事件阈值触发 |
| 进程隔离 | 需 OS 支持 | 内核态实现 | 硬件 procTag |
| 适用场景 | 通用 | Linux 系统级 | BOOM 微架构研究 |
| 对处理器核修改 | 无 | 无 | 需修改 RTL |
| 用户态可用 | 受 `mcounteren` 控制 | 通过 perf_event_open | 直接可用 |

BOOM-stop 的核心优势在于：（1）计数器控制完全在用户态完成，无需操作系统支持，适合裸机测试和 SimPoint 检查点恢复等场景；（2）预热和采样由硬件自动管理，避免了软件插桩引入的干扰；（3）63 个预定义事件覆盖了 BOOM 处理器全流水线关键微架构行为，可直接用于详细的性能瓶颈分析。

## 2 框架原理

### 2.1 指令编码复用机制

BOOM-stop 的软件控制机制基于一个关键观察：在 RISC-V 指令系统中，`addi x0, rs1, imm` 形式的指令（目标寄存器为 `x0`）在标准语义下不改变任何体系结构状态（因为 `x0` 恒为零），等价于 NOP 指令。BOOM-stop 利用这一特性，将该指令编码复用为性能计数器的控制指令：

- **设置控制寄存器**：`addi x0, rs1, tag`，其中 `tag`（即立即数字段）指定要设置的控制寄存器类型，`rs1` 提供要写入的值。
- **复位所有计数器**：`addi x0, x0, 127`，将所有事件计数器清零。
- **读取计数器**：`addi x0, rs1, 128+N`，将第 N 个计数器的值读取到 `rs1` 指定的寄存器中。

处理器在译码阶段识别到 `addi` 指令且目标寄存器为 `x0` 时，检查立即数字段的值。如果立即数落在 BOOM-stop 定义的控制范围内（而非标准的 `addi x0, x0, 0` 即 NOP），处理器会执行对应的计数器控制操作，而非将其作为普通 NOP 丢弃。

这一设计的优势在于：

1. **无需新增指令编码**：完全复用已有的 RISC-V 指令，不违反指令系统规范（`x0` 的写入被忽略），不会影响已有的程序正确性。
2. **用户态可执行**：`addi` 是非特权指令，无需切换到 M 态或 S 态即可控制计数器。
3. **零架构状态副作用**：控制指令在 RISC-V 标准语义下不修改任何可见的寄存器或内存状态，对程序行为完全透明。

### 2.2 硬件控制寄存器

BOOM-stop 在处理器核心中新增了一组控制寄存器，通过 `addi x0, rs1, tag` 指令进行设置（`tag` 对应不同的控制寄存器）：

| tag 值 | 寄存器名称 | 功能说明 |
|--------|-----------|---------|
| 1 | `procTag` | 进程标识寄存器。操作系统在进程切换时保存/恢复该标识，子进程继承父进程的标识。用于区分不同进程的事件贡献 |
| 2 | `sampleFuncAddr` | 采样处理函数入口地址。当设置为 0 时，采样事件触发系统调用（由 ptrace 工具捕获）；非零时处理器直接跳转到该地址执行采样处理函数 |
| 3 | `sampleEventSel` | 采样事件选择。取值为 `rs1 % 8`，默认为 0（按指令数采样）。可选择不同的微架构事件作为采样触发源 |
| 4 | `maxEventNum` | 采样事件阈值。当选定的采样事件累计达到该值时触发采样动作 |
| 5 | `warmupInstNum` | 预热指令数。当用户态指令数达到该值时，硬件自动复位所有事件计数器，进入正式测量阶段 |
| 6 | `pfc_maxPriv` | 计数器权限级别。控制计数器采集哪些特权级别的事件：0=仅用户态、1=用户态+监管态、3=全部级别 |
| 7 | `pfc_enable` | 计数器使能。设置计数器是否工作。采样触发时硬件自动将该位清零以暂停计数 |
| 8 | `sampleHappen` | 采样发生标记。采样触发时由硬件置位，用于通知软件当前系统调用或跳转是由采样事件引发的 |
| 9-12 | `temp1`~`temp4` | 临时寄存器。用于采样处理函数中保存/恢复上下文，避免修改用户程序的寄存器状态 |

### 2.4 预热与采样机制

BOOM-stop 内建了两个核心自动化机制，使其与 SimPoint 方法论无缝配合：

**预热自动复位：** 当软件设置了 `warmupInstNum` 后，硬件在用户态指令数达到该阈值时自动将所有 63 个事件计数器清零。这一机制确保预热阶段（用于填充缓存、分支预测器等微架构状态）积累的事件计数不会污染正式测量阶段的数据，无需软件在预热结束点手动插桩。

**事件阈值采样：** 当某个选定的采样事件（由 `sampleEventSel` 指定）的累计值达到 `maxEventNum` 设定的阈值时，硬件触发采样动作。采样触发时，处理器自动执行以下操作：（1）将 `pfc_enable` 清零以暂停计数；（2）置位 `sampleHappen` 标记；（3）根据 `sampleFuncAddr` 的设置，跳转到采样处理函数或触发系统调用。默认的采样事件为指令数（`sampleEventSel = 0`），即每执行 `maxEventNum` 条指令触发一次采样。

### 2.5 BOOM 处理器的 RTL 修改

BOOM-stop 的硬件修改集中在 BOOM 处理器核心的 Chisel 源码中，主要涉及以下模块：

1. **译码逻辑**：识别 `addi x0, rs1, imm` 指令中的特殊立即数值，将其路由到控制寄存器写入逻辑或计数器读取逻辑。
2. **核心控制逻辑**：新增控制寄存器组（`procTag`、`warmupInstNum`、`maxEventNum` 等）和 63 个事件计数器寄存器，以及预热复位和采样触发的硬件状态机。
3. **全流水线事件采集**：在取指、译码、分发、发射、执行、访存等各阶段插入事件信号的采集逻辑，将对应信号接入事件计数器的递增输入。

RTL 代码的修改通过两个标注进行标识：
- `Enable_PerfCounter_Support`：事件计数器和控制寄存器相关的修改。
- `Enable_Sample_Support`：采样触发和跳转相关的修改。

## 3 使用方法

### 3.1 硬件侧准备

1. 将 BOOM-stop 的硬件修改合并到 BOOM V3 的 Chisel 源码中。修改涉及的核心文件为 `core.scala`（核心控制逻辑）和 `lsu.scala`（访存子系统事件）等。
2. 根据研究需要，在事件计数器列表中增加或修改自定义事件。例如，本文方案新增了 Tracing Map 快速地址转换命中次数、SAB 冲突检测次数、推测式唤醒相关统计等自定义事件。
3. 通过 Chipyard 构建流程生成 Verilog RTL，再通过 Verilator 编译仿真二进制或通过 Vivado 综合 FPGA 比特流。

### 3.2 软件侧使用

BOOM-stop 提供了两种软件侧的使用方式：

#### 3.2.1 方式一：程序内自行处理（Self-Handle）

该方式将计数器控制代码直接嵌入到被测程序中，适用于裸机测试或 SimPoint 检查点恢复场景。

**典型使用流程：**

```c
// 1. 设置控制寄存器（通过内联汇编实现 addi x0, rs1, tag）
set_procTag(0x1234567);                // tag=1: 设置进程标识
set_sampleFuncAddr(sample_handler);    // tag=2: 设置采样处理函数地址
set_warmupInstNum(1000000000);         // tag=5: 设置预热指令数为10亿
set_maxEventNum(200000000);            // tag=4: 设置测量指令数为2亿
set_pfc_maxPriv(0);                    // tag=6: 仅统计用户态事件
set_pfc_enable(1);                     // tag=7: 启动计数器

// 2. 执行被测程序...
// （硬件在预热阶段结束时自动复位计数器）
// （测量阶段结束时硬件自动触发采样）

// 3. 在采样处理函数中读取计数器
void sample_handler() {
    uint64_t cycles, insts, dtlb_access, dtlb_miss;
    read_counter(0, &cycles);       // addi x0, rs1, 128: 读取第0个计数器（cycles）
    read_counter(1, &insts);        // addi x0, rs1, 129: 读取第1个计数器（insts）
    read_counter(33, &dtlb_access); // addi x0, rs1, 161: 读取第33个计数器
    read_counter(34, &dtlb_miss);   // addi x0, rs1, 162: 读取第34个计数器
    // ... 输出或保存结果
}
```

BOOM-stop 提供了两种嵌入方式：
- **二进制链接方式**（`example/self_handle/binary/`）：将采样设置和处理函数编译为独立的 `.o` 文件，被测程序在编译链接时将其链接即可，无需修改被测程序的源码。
- **头文件包含方式**（`example/self_handle/include_files/`）：提供采样设置和处理函数的头文件，在被测程序中直接 `#include` 并在适当位置调用。

**采样处理函数的实现要点：**
- 利用 `__attribute__((constructor))` 在程序入口前自动完成控制寄存器的初始化设置。
- 使用 BOOM-stop 提供的临时寄存器（`temp1`~`temp4`）保存和恢复上下文，避免修改用户程序的寄存器。
- 采样函数中分配独立的栈空间（`tempStackMem`），防止覆盖用户程序的栈数据。
- 避免在采样函数中使用 `printf`（会导致死锁），改用 `sprintf` + `write` 组合进行输出。
- 采样处理完成后，通过 `URet` 指令（`addi x0, x0, 64`）跳转回被中断的用户程序继续执行。

#### 3.2.2 方式二：ptrace 外部工具捕获

该方式通过一个外部工具程序利用 `ptrace` 系统调用追踪被测程序的执行，无需修改被测程序本身。

**工作原理：**

1. 工具程序通过 `fork` 创建子进程。
2. 子进程设置 `procTag` 和 `sampleFuncAddr = 0`（设为 0 表示采样触发时引发系统调用而非跳转）。
3. 子进程通过 `execv` 启动被测程序。
4. 父进程通过 `ptrace` 追踪子进程的系统调用。
5. 当检测到系统调用且 `sampleHappen` 寄存器被置位时，父进程判定这是一次采样事件触发的系统调用，执行计数器读取和数据采集。
6. 父进程修改子进程的系统调用号为未实现的调用号（避免系统调用实际执行修改内存），重新设置采样控制寄存器，恢复子进程继续运行。

该方式的优势在于对被测程序完全透明，适用于无法修改源码的场景。

### 3.3 计数器读取指令汇总

| 操作 | 指令格式 | 说明 |
|------|---------|------|
| 设置控制寄存器 | `addi x0, rs1, tag` | tag=1~12，rs1 为写入值 |
| 复位所有计数器 | `addi x0, x0, 127` | 将 63 个计数器全部清零 |
| 读取第 N 个计数器 | `addi x0, rs1, 128+N` | 将第 N 个计数器的值写入 rs1 |
| 读取 userExitPC | `addi x0, rs1, 35` | 读取采样跳转前的最后一条指令地址 |
| URet 跳转 | `addi x0, rs1, 64` | 根据 temp 寄存器进行跳转返回 |

### 3.4 输出数据格式

BOOM-stop 的输出以 JSON 行格式记录，每行一个事件：

```json
{"type": "max_inst", "times": 1, "cycles": 2390605069, "inst": 1286464490}
{"type": "event  0", "value": 364486085}
{"type": "event  1", "value": 200003995}
{"type": "event  2", "value": 218459445}
...
{"type": "event 62", "value": 11131186}
```

其中：
- `max_inst` 行记录采样触发时的总周期数和总指令数。
- `event N` 行记录第 N 个计数器在测量阶段的累积值。
- 数据文件可由 Python 等脚本解析，用于计算 IPC、缺失率等性能指标。

### 3.5 自定义事件扩展

研究人员可根据需要在 BOOM-stop 的基础上扩展自定义事件。扩展步骤如下：

1. 在 `core.scala` 的事件计数器数组中增加新的计数器条目。
2. 将需要统计的硬件信号接入新计数器的递增输入。例如：

```scala
// 在 core.scala 中新增自定义事件（示例）
perfEvents(63) := custom_event_signal  // 将自定义信号接入第63个计数器
```

3. 更新分析脚本中的事件编号映射，使其能够正确解析新增事件的计数值。

本文方案即在 BOOM-stop 的基础上新增了以下自定义事件计数器：Tracing Map 快速地址转换命中次数、Tracing Map 装入回写更新次数、Tracing Map 立即数偏移更新次数、SAB 冲突检测次数、推测式唤醒总次数、推测式唤醒（重试路径）次数、推测式唤醒失败次数以及推测式唤醒失败（重试路径）次数等，用于对方案各子模块的行为进行细粒度的硬件级观测。

## 4 SimPoint 检查点切片流程

BOOM-stop 的性能评测依赖于 SimPoint 方法论进行代表性片段的采样。由于 SPEC CPU 基准程序的完整执行通常涉及数千亿条指令，直接在周期精确仿真或 FPGA 上完整运行是不现实的。SimPoint 检查点切片技术通过提取程序执行中具有代表性的片段，使得在可接受的时间内完成性能评测成为可能。该流程涉及配套工具 [gem5_riscv_ckpt](https://github.com/Shuiliusheng/gem5_riscv_ckpt)，整个工作流分为四个阶段。

### 4.1 阶段一：BBV 采集与 SimPoint 聚类分析

SimPoint 方法论的第一步是对程序的动态执行行为进行特征提取和聚类分析，确定需要创建检查点的位置。

**1）基本块向量（BBV）采集。** 使用 gem5 功能级仿真器（`gem5.fast`，使用 `NonCachingSimpleCPU` 即无缓存的简单 CPU 模型）完整执行目标程序，将动态指令流按固定长度（通常为 1 亿条指令）划分为若干区间。对每个区间统计各基本块（Basic Block）的执行频率，构成该区间的 BBV 特征向量。BBV 反映了程序在该区间内的控制流行为特征。

**2）聚类分析。** 使用 SimPoint 工具对所有区间的 BBV 进行 K-means 聚类，将行为相似的区间归为同一阶段（Phase）。聚类完成后，每个簇产生一个代表性区间（即 SimPoint），并记录该簇的权重（所含区间数占总区间数的比例），权重越大表示该阶段在程序执行中占比越高。

**3）代表性区间选取。** 从每个聚类中选取距聚类中心最近的区间作为该阶段的代表性片段。在实际评测中，通常选取权重最大的一个或若干个 SimPoint 进行仿真。

### 4.2 阶段二：使用 gem5 创建检查点文件

确定了 SimPoint 位置后，使用 gem5_riscv_ckpt 工具创建对应位置的检查点（Checkpoint）文件。检查点文件记录了程序在该时刻的完整微架构状态快照，使得后续可以直接从该点恢复执行，而无需重新执行前序数千亿条指令。

**创建命令示例：**

```bash
./build/RISCV/gem5.fast ./configs/example/se.py \
    --cpu-type=NonCachingSimpleCPU \
    --mem-type=SimpleMemory \
    --mem-size=8GB \
    --ckptsetting=settingsfile \
    -c bench/test.riscv --options=""
```

其中 `--ckptsetting` 指定的配置文件控制检查点的创建参数：

```
stacktop: 0x3e00000000          # 运行时栈基址
mmapend: 0x0e00000000           # mmap 起始位置
ckptprefix: ./ckpt_dir/test     # 输出检查点文件的目录和前缀
strictLength:                   # 严格按指令数截断（不等待退出指令）
ckptctrl: 300200000000 1200000000 1000000000 1
# 参数含义：起始指令位置 片段长度 预热指令数 创建数量
```

`ckptctrl` 行的四个参数说明：
- `startckpt`：从第多少条指令开始创建检查点（即 SimPoint 分析得出的起始位置）。
- `interval`：检查点片段的总指令长度（包含预热和测量）。
- `warmupnum`：预热指令数，恢复时先执行这些指令填充微架构状态。
- `times`：创建几个检查点。

**检查点文件记录的内容：**

gem5 在功能级仿真过程中，当执行到指定的指令位置时，记录以下状态信息并生成检查点文件（`.info` 格式）：

| 内容 | 说明 |
|------|------|
| 整数/浮点寄存器 | 32 个整数寄存器和 32 个浮点寄存器在检查点起始处的完整值 |
| PC（程序计数器） | 检查点起始处的下一条指令地址 |
| 代码段信息 | 片段执行期间访问的代码段区域（地址范围） |
| 内存区域信息 | 片段执行期间访问的数据内存区域（以 4KB 页为单位） |
| First Load 信息 | 片段中每条装入指令首次访问的地址和数据值，用于冷启动时初始化缓存状态 |
| 系统调用信息 | 片段执行期间发生的系统调用的参数、返回值和内存修改记录 |
| 退出信息 | 片段结束处的 PC 地址和退出原因 |

其中 **First Load 信息** 是检查点技术的关键：由于检查点恢复时缓存和 TLB 均为空，第一次装入某地址的数据无法从缓存获得，必须由检查点文件提供正确的数据值。gem5_riscv_ckpt 通过追踪每个地址的首次装入来记录这些信息，并使用 fastlz 压缩算法减小文件体积。

**加速创建：** 对于需要创建多个不同片段的场景，gem5_riscv_ckpt 支持基于已有检查点二次切片：先创建指令数较大的粗粒度检查点，再通过 `readckpt_new.riscv` 加载并执行已有检查点文件，在此基础上创建更细粒度的新检查点，避免每次都从程序起始位置重新执行。

### 4.3 阶段三：在 FPGA 上恢复检查点并执行

检查点文件创建完成后，需要在目标平台（Verilator 仿真器或 FPGA）上恢复并执行。恢复由一个专门的加载器程序（`readckpt.riscv`）完成。

**恢复流程如下：**

```
readckpt.riscv  +  检查点文件(.info)  →  在 BOOM 处理器上恢复执行
```

加载器 `readckpt.riscv` 的执行步骤（对应日志输出中的 step 标记）：

1. **加载 ELF 和代码段**（step 1）：读取检查点起始 PC，分配并映射代码段内存区域。
2. **恢复寄存器**（step 2）：将检查点中保存的 32 个整数寄存器和 32 个浮点寄存器的值写入对应寄存器。
3. **恢复内存区域**（step 3）：根据检查点中记录的内存区域信息，分配并映射数据内存页。
4. **初始化 First Load 数据**（step 4）：将 First Load 信息中记录的地址-数据对写入对应内存位置，确保恢复后首次装入能获得正确数据。
5. **配置系统调用代理**（step 5）：如果检查点中有系统调用记录，配置系统调用的拦截和重放机制；如果无系统调用，将退出指令替换为跳转指令。
6. **设置跳转和采样参数**（step 6）：将起始 PC 写入临时寄存器，配置 BOOM-stop 的控制寄存器（预热指令数、最大指令数、采样函数地址等）。
7. **切换上下文并开始执行**（step 789）：保存加载器自身的寄存器状态，加载被测程序的寄存器状态，跳转到检查点的起始 PC 开始执行。

**执行过程中 BOOM-stop 的配合：**

恢复执行后，BOOM-stop 的硬件机制自动接管性能数据采集：

```
|← ——— 预热阶段（10亿条指令）——— →|← — 测量阶段（2亿条指令） — →|
|  填充缓存/预测器/Tracing Map      |  计数器自动复位并开始计数    |
|                                    |  达到阈值后触发采样          |
```

- 加载器在启动时设置 `warmupInstNum = 1000000000`（10 亿条指令预热）和 `maxEventNum = 200000000`（2 亿条指令测量）。
- 硬件执行到预热阈值时自动复位所有 63 个计数器。
- 继续执行 2 亿条指令后，硬件触发采样事件，跳转到采样处理函数。
- 采样处理函数读取所有计数器值并输出至日志文件，格式为上文所述的 JSON 行格式。

### 4.4 阶段四：数据采集与分析

采样完成后，日志文件包含了 63 个事件计数器在测量阶段的累积值。使用 Python 分析脚本对日志进行解析，计算各项性能指标：

```
日志文件(.log) → Python 分析脚本 → IPC/缺失率/覆盖率等指标 + 对比图表
```

典型的分析流程：
1. 解析每个基准程序在各配置下（Baseline、Tracing Map、+ADDI、+SAB、+Spec）的日志文件。
2. 从 `event 0`（cycles）和 `event 1`（insts）计算 IPC。
3. 从 `event 33`（dtlb_access）和 `event 34`（dtlb_miss）计算 D-TLB 缺失率。
4. 从自定义事件计数器提取 Tracing Map 覆盖率、SAB 冲突次数、推测式唤醒统计等方案特有指标。
5. 跨配置对比生成变化率图表。

### 4.5 完整工作流总结

```
┌─────────────────────────────────────────────────────────────────┐
│ 阶段一：SimPoint 分析                                            │
│   SPEC CPU 程序 → gem5 功能级仿真 → BBV 采集 → K-means 聚类       │
│   → 确定代表性片段位置和权重                                       │
├─────────────────────────────────────────────────────────────────┤
│ 阶段二：检查点创建                                                │
│   gem5 + gem5_riscv_ckpt → 在 SimPoint 位置创建 .info 检查点文件  │
│   （记录寄存器、内存、First Load、系统调用等完整状态）               │
├─────────────────────────────────────────────────────────────────┤
│ 阶段三：FPGA 恢复与执行                                          │
│   readckpt.riscv 加载 .info → 恢复程序状态 → BOOM-stop 控制采样   │
│   → 预热阶段自动复位 → 测量阶段计数 → 触发采样输出日志              │
├─────────────────────────────────────────────────────────────────┤
│ 阶段四：数据分析                                                  │
│   日志文件 → Python 脚本 → IPC/缺失率/覆盖率等指标 → 对比图表      │
└─────────────────────────────────────────────────────────────────┘
```

这一完整工作流使得在 FPGA 平台上对 20 个 SPEC CPU 基准程序、5 种配置的性能评测成为可能，每个程序的 FPGA 执行时间从完整运行的数周缩短至数小时以内。
