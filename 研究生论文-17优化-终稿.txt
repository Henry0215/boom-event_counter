硕士研究生学位论文

题目：
跟踪基址的装入延迟隐藏机制的设计与实现

　　

摘要
装入指令通常位于数据依赖链根部，其执行延迟沿依赖链向下游传播，是制约超标量乱序处理器单线程性能的关键因素之一。如何降低装入指令的延迟，已成为高性能处理器微架构设计的重要研究课题之一。本文提出一种跟踪基址的装入地址预测机制及其实现方法，利用装入指令的基址寄存器在回写时可被译码阶段观测这一特性，在译码阶段维护寄存器缓存基地址，使装入指令提前获取装入地址，绕过发射和读寄存器阶段直接进入访存流水线，从而减少装入指令经过的流水级，进而降低下游依赖指令的等待延迟。
本文的主要工作包括：
1）调研并分析了装入地址提前获取与指令发射优化、存储相关预测以及依赖指令推测式调度等相关技术，明确了装入地址预测及相关优化的技术路线与设计空间。
2）设计并实现了以地址映射表为核心的装入地址预测机制。地址映射表在译码阶段跟踪寄存器与装入指令基地址的映射关系，实现装入地址的提前解析；通过立即数偏移融合扩展地址跟踪的覆盖范围以提高映射表命中率；引入存储地址缓冲区预检测缓解因提前访存引入的存储-装入内存序违例；扩展推测式唤醒机制进一步缩短依赖指令的等待延迟。
3）基于 RISC-V 开源处理器 BOOM V3 实现本文方案，通过 FPGA 原型平台运行 SPEC CPU 2006 和 SPEC CPU 2017 基准程序进行验证与评测。实验结果表明，在 MediumBOOM 配置下，本文方案实现了 2.85% 的平均 IPC 提升，验证了该方法能在可控的硬件资源开销下有效缩短装入指令执行延迟，为超标量处理器的装入地址预测提供了一种实用的解决途径。

　　
　　
　　
　　
　　
　　
　　
关键词：超标量处理器，RISC-V处理器，装入指令，访存地址预测
　　

English Title
Fu Shaohong (Computer Architecture)
Directed by Professor Liu Xianhua
Abstract
　　Load instruction execution latency is one of the key bottlenecks restricting the single-threaded performance of superscalar out-of-order processors. Load instructions constitute a large proportion of dynamic instructions and are generally located at the root of the data dependency chain. Their latency propagates downstream through the dependency chain, significantly impacting the overall pipeline throughput. Reducing the effective execution latency of load instructions is an important research direction for improving the single-threaded performance of processors.
　　This paper, combining research on load instruction latency optimization techniques, designs and implements a base address-tracking load latency hiding mechanism, and implements and evaluates it based on the RISC-V open-source processor BOOM V3. The main contributions of this paper can be summarized as follows:
　　1. A survey and analysis of related work was conducted, including load instruction latency optimization and instruction issue optimization, memory dependence prediction, and dependent instruction speculative scheduling techniques. These three types of work all aim to reduce the latency caused by load instructions to the overall system and can work together to improve processor execution efficiency.
　　2. A base address-tracking load latency hiding mechanism was designed and implemented based on the BOOM V3 processor. First, the pipeline of the BOOM V3 processor was analyzed, and the complete execution flow of the load instruction was analyzed in detail, revealing the source of latency bottlenecks. Based on this, the design concept of the proposed solution was described in detail, and the four modules were explained: the Tracing Map core module reduces load instruction latency by pre-parsing the load address during the decoding stage, bypassing the issue queue; the immediate offset fusion extension improves the Tracing Map hit rate by tracking immediate addition and subtraction; SAB conflict pre-detection alleviates the memory-load order violation problem by obtaining the memory address in advance; and the speculative wake-up extension further optimizes the waiting latency of dependent instructions.
　　3. Correctness verification and performance evaluation of the proposed solution were conducted. Experiments were performed using Verilator cycle-accurate simulation and an FPGA platform. Multi-level testing confirmed functional correctness, and performance evaluation was conducted based on the SPEC CPU 2006 benchmark and SPEC CPU 2017 benchmark programs. Experimental results show that a 2.85% IPC improvement was achieved on the FPGA platform under MediumBOOM configuration.
　　
　　KEY WORDS: Superscalar Processor, RISC-V Processor, Load Instruction, Memory Address Prediction

第一章　 绪论
1.1　 研究背景与意义
1.1.1　 研究背景
　　随着集成电路相关技术与工艺的持续演进，现代高性能处理器的指令级并行（Instruction-Level Parallelism, ILP）能力得到了较大的提升。超标量（Superscalar）处理器通过乱序执行（Out-of-Order Execution）、寄存器重命名（Register Renaming）等技术，能够在每个时钟周期内发射并执行多条指令，显著提升了处理器执行单个程序的性能[1]。然而，伴随着处理器核心计算速度的快速增长，而存储系统访问速度的提升却较慢，这导致了存储系统的访问逐渐成为了处理器性能的瓶颈，该问题也被称为“存储墙”（Memory Wall）[2]。  
图1.1　处理器的存储器请求与DRAM访问延迟的时间变化[3]
　　该矛盾在当前通用计算场景中较为显著。一方面，云计算、数据库等各类具有代表性的负载普遍具有复杂的数据访问模式，内存访问表现出一定的随机性与不规则性，这会导致处理器的访存挑战更大；另一方面，尽管多核技术能够在系统层面上分担计算压力，但单核性能仍直接决定了大量串行和延迟敏感任务的性能表现。因此，在不显著增加功耗和面积开销的前提下提升处理器单核的访存效率，仍是高性能处理器设计中的核心问题之一。
　　有三类手段可以提高访存效率：其一是改进存储层次结构（如更大的高速缓存或更激进的预取）；其二是提升访存并行度（如更大的发射宽度和更复杂的内存调度方式）；其三是缩短关键访存指令的执行路径的延迟。相比前两类方法在工业界已被广泛采用，直接降低关键装入指令在流水线中的有效延迟的方法，往往可以以更小的硬件代价获得可观的性能收益。
　　在超标量乱序处理器的流水线中，装入（Load） 指令占据着重要的地位，是提升处理器访存效率的关键所在。根据典型工作负载的统计，装入指令约占全部动态指令的 20% 至30% [4]。本研究基于RISC-V指令系统[5]的处理器在 SPEC CPU 2006和SPEC CPU 2017 SimPoint基准测试集[6]上的实测数据也验证了这一范围：在运行的基准程序中，提交的装入指令占总提交的指令数的平均值为 25.3%；若将存储（Store）指令一并计入，访存指令的合计平均占比达 35.4%。更重要的是，装入指令往往都位于数据依赖链的关键路径上：大量后续的算术、逻辑和分支指令都依赖于装入指令的返回数据。因此，装入指令的执行延迟直接决定了这些对装入指令有数据依赖的指令的发射时机，对处理器的整体执行效率有着显著的影响。
图1.2　SPEC CPU 2006和SPEC CPU 2017 SimPoint访存指令占比
　　在现代乱序超标量处理器微架构中，一条典型的装入指令从取指到最终提交，需要经历多个阶段：在经过取指（Fetch）、译码（Decode）、重命名（Rename）后，装入指令会经过分发（Dispatch）阶段将指令分配到发射队列（Issue Queue, IQ）中等待源操作数就绪，然后再在发射（Issue）阶段被发射并读取源操作数后进入装入-存储部件（Load Store Unit, LSU），在装入-存储部件中进行虚实地址转换后再访问存储器获得数据。在此期间，所有依赖该装入指令的数据的指令均会被阻塞在发射队列中，就可能会造成流水线气泡，进而可能导致 IPC（Instructions Per Cycle）的降低。
　　由上所述，在现代超标量乱序处理器的微架构中，一条装入指令的延迟通常可分解为：处理器前端到发射阶段的流水线延迟、发射队列的仲裁延迟、地址生成与地址翻译的延迟以及缓存命中或未命中导致的数据返回的延迟等。在一级数据缓存命中的理想情况下，前两类延迟就可能会成为关键路径，尤其是在发射队列压力较大、端口竞争激烈或同时存在长延迟指令时更为明显。这意味着仅从高速缓存以及预取的角度来优化访存并不足以完全解决装入指令的延迟对处理器整体吞吐存在影响的问题。
　　为了缓解该问题，现代处理器已经采用了推测式唤醒（Speculative Wakeup）机制，在装入指令访问存储器之前就乐观地唤醒依赖其数据的指令，以部分隐藏装入指令的延迟。但该机制受限于装入指令必须先被发射队列选择并发射。在发射队列资源紧张或存在长延迟指令占用的情况下，装入指令本身的发射就可能被延迟数个周期，进而推迟整个依赖链的执行。此外，当推测式唤醒失败（例如转换旁视缓冲器（TLB）未命中或一级高速缓存（L1 Cache）未命中）时，处理器需要重放（Replay）被错误唤醒的指令，造成额外的性能损失和功耗开销。
	此外，即使装入指令的延迟降低，也不一定会提升处理器的性能。由于超标量乱序处理器对存储指令的乱序执行，装入指令和存储指令之间的执行顺序可能会被打乱，且装入指令的延迟降低可能会加剧这一情况。为了保证程序执行的正确性，需要维护对访问相同地址的装入指令和存储指令的读写依赖的限制。如果一条装入指令先于其前序的且访问地址相同的存储指令执行，就会产生内存序违例（Memory Order Violation）而引发异常并回滚（Rollback），反而会导致性能的下降。
1.1.2　 研究意义
　　鉴于装入指令对现代处理器性能有着显著影响，围绕降低装入指令的执行延迟的研究一直受到业界的广泛关注。本文工作主要关注以下方面：
　　（1）装入地址提前获取与提前执行。如果能够在流水线的早期阶段（如译码阶段）预先获得装入指令的目标地址，装入指令就可以绕过发射队列的等待，提前访问存储器，从而缩短单条装入指令的延迟。Austin 和 Sohi 早在 1995 年就提出了“零周期装入”（Zero-cycle Loads）的概念[7]，利用步进（Stride）模式预测装入指令的目标地址。近年来，苹果的商业处理器中也发现内置了装入地址预测器（Load Address Predictor, LAP）[8]，表明这一类型的技术已在商用处理器中得到了实际部署。
　　（2）存储相关预测（Memory Dependence Prediction, MDP）。乱序执行处理器中装入指令与先序的存储指令之间的存储相关（Memory Dependence）关系是制约装入指令提前执行的另一重要因素。存储相关预测技术通过预测存储和装入指令之间的依赖关系，允许预测无依赖的装入指令绕过未解析的存储指令提前执行，在不显著增加内存序违例的同时提高访存并行度。
　　（3）推测式唤醒。即使装入指令能够提前发射，其依赖指令的唤醒时机仍然影响性能。推测式唤醒技术通过预测装入指令的缓存命中的延迟，提前唤醒依赖其数据的指令，以便在装入的数据返回时就能让依赖指令立即使用。
1.2　 本文主要工作
　　本文的工作为跟踪基址值的装入指令延迟隐藏机制的设计与实现。本文参考基于追踪寄存器的装入指令的地址提前解析的方案[9]，从以下角度出发：在超标量处理器的译码阶段引入一个轻量级的地址计算的单元 Tracing Map，通过将装入指令的基地址值（base register value）缓存于对应逻辑寄存器表项，使得命中的装入指令在译码时即可计算出地址。命中的装入指令会绕过发射队列，直接进入装入队列，并通过装入-存储部件的重试路径完成虚实地址转换和缓存访问，从而节省了发射队列排队和访问寄存器堆的延迟。在此基础上，本文进一步提出了三项协同优化：
　　立即数加减累积偏移优化：识别并追踪基址寄存器的立即数加减法的自增模式，将步进偏移累积到计算地址中，大幅提升 Tracing Map对例如循环顺序访问模式的覆盖率。
　　地址冲突预检测：在分发阶段利用提前计算出的存储指令的目标地址进行轻量级的存储-装入冲突检测，降低因为Tracing Map提前执行的装入指令而导致的内存序违例（Memory Order Violation）风险。
　　推测式唤醒扩展：将处理器原有的推测式唤醒机制扩展覆盖新的绕过发射的装入指令路径，使绕过发射队列的装入指令也能推测式地唤醒其依赖指令，进一步缩短从装入指令发射到依赖指令执行的延迟。
　　具体而言，本文的工作内容如下：
1） 针对装入地址提前获取及指令发射优化、存储相关预测以及推测式唤醒的相关内容进行调研，对该领域内一些代表性的工作进行分析，归纳整理了这些领域的挑战以及研究现状。

第二章　 相关工作
　　本章围绕本文工作所使用的优化技术，对相关的装入指令延迟优化的技术进行阐述。正如上文所述，装入指令的执行延迟是制约超标量乱序处理器性能的核心因素之一。围绕缩短装入指令的有效延迟这一目标，学术界和工业界在过去三十余年间开展了大量研究工作，形成了多个研究方向。这其中有：
　　第一，如何更早地获取装入指令的目标地址。在传统的乱序执行流程中，装入指令必须等待基址寄存器就绪后才能计算地址并发起访存请求。如果能在流水线的更早阶段——甚至在操作数就绪之前——获取装入指令的目标地址，就可以提前发起访存请求，从而缩短从指令进入处理器后端到数据就绪的总延迟。
　　第二，如何安全地允许访存指令的乱序执行。乱序执行的处理器中，装入指令可能绕过尚未完成地址计算的先序存储指令提前执行。如果该装入与某条先序的存储指令访问了相同的内存地址，就会产生内存序违例（Memory Order Violation），处理器需要以较高的代价进行恢复。存储相关预测（Memory Dependence Prediction, MDP）技术旨在预测装入-存储的存储相关的关系，阻止有冲突的装入指令的提前执行以避免异常。
　　第三，如何最大化装入延迟对依赖链的隐藏效果。即使装入指令能够尽早发射，其返回的数据到达依赖指令仍需要若干周期。推测式调度（Speculative Scheduling）技术通过预测装入指令的命中延迟，在装入指令的数据实际返回之前提前唤醒依赖指令，使依赖指令的发射与装入指令的存储访问相重叠，从而进一步隐藏延迟。
　　这三个子问题并非是孤立的。地址预测使装入指令更早发射，但提前执行的装入指令面临更高的存储-装入冲突风险，且提前发射的装入指令也需要配合推测式唤醒才能充分发挥延迟缩短的收益。本文提出的方案正是从这一系统性视角出发，同时在三个维度上进行协同优化。
2.1　 装入地址提前获取与指令发射优化相关技术概述
　　在乱序超标量处理器的执行引擎中，发射队列（Issue Queue, IQ）是连接执行单元的核心调度枢纽。发射队列负责缓存已译码但尚未执行的指令（即处于等待执行状态的微指令），并通过唤醒-选择（Wakeup-Select）逻辑在操作数就绪后将指令发射至相应的执行单元。从微架构实现的角度看，发射队列本质上是一个内容可寻址存储器（Content-Addressable Memory, CAM）结构：每当一条指令产生结果并广播其目标寄存器标识时，发射队列中所有等待该寄存器的指令条目会同时被唤醒（Wakeup），标记其对应的操作数已就绪；随后，选择逻辑（Select Logic）从所有操作数完全就绪的指令中按优先级选出一条或多条发射至执行端口，交给执行单元执行。
　　发射队列的设计面临容量与时序的尖锐矛盾。一方面，更大的发射队列能够缓存更多的指令，增大处理器的有效指令窗口，从而提升 ILP 的挖掘能力；另一方面，发射队列的内容可寻址存储器匹配延迟和优先级选择延迟随条目数的增加而增长，构成处理器时钟频率的关键路径，Palacharla 等人[10]对此问题进行了系统性的量化分析。在实际设计中，发射队列的容量通常远小于重排序缓冲器（ROB）的容量，这意味着发射队列是处理器后端中较为稀缺的资源，当发射队列被填满时，分发（Dispatch）阶段将被阻塞（Stall），即使重排序缓冲器中仍有空间，新指令也无法进入后端。
　　对于装入指令而言，发射队列带来的延迟尤为显著。一条装入指令在进入发射队列后，需要经历以下阶段：（1）等待基址寄存器就绪；（2）发射端口仲裁；（3）经过地址生成单元计算虚拟地址、访问装入-存储部件，经过转换旁视缓冲器进行地址翻译、访问一级数据高速缓存获取数据。整个流程从装入指令进入发射队列到数据返回，构成了一条经过调度器和存储子系统的长延迟链。如果能在发射队列之前（甚至在译码阶段）就获取装入指令的目标地址，使装入指令绕过发射队列的等待和仲裁阶段直接发起缓存访问，就可以避免这部分的延迟开销。这正是装入地址预测（Load Address Prediction）技术的核心动机。
2.1.1　 装入地址预测与优先调度
　　对装入地址提前获取的方案的研究包含有如下两类：一类方法试图在不改变访存层次结构的前提下，通过预测直接缩短装入指令的执行路径（例如地址提前解析、地址预测）。另一类方法则将装入指令或其地址计算相关指令进行优先化调度，降低其在共享资源中的排队时间。前者通常收益更直接，但对预测精度或可追踪性要求较高；后者对正确性更稳健，但优化幅度常受限于调度窗口与资源竞争状态。因此，如何在低硬件开销条件下同时获得较高覆盖率与可实现性，成为该方向持续关注的问题。此外，装入值预测（Load Value Prediction）[11]试图直接预测装入指令返回的数据值从而跳过缓存访问，但由于其预测精度和硬件开销等问题在实际应用中受到限制，本文主要关注地址层面的优化技术。
　　零周期装入（Zero-cycle Loads）[7]采用的思路即是地址预测的思路，通过预测装入地址而提前使用装入地址访问存储器，以此降低装入指令的执行延迟。Austin在 1995 年提出了该方案，其核心思想是利用装入指令访问的地址的可预测性：程序中大量装入指令访问的地址遵循步进（Stride）模式或上次值（Last Value）模式。他们提出使用基于程序计数器（Program Counter，PC）索引的增量表（Delta Table）预测装入指令访问的地址，根据该表存储的预测值提前获取对应的地址，在地址计算之前就向缓存发起投机的访问。当预测正确时，装入指令表现为解码阶段结束进入执行阶段之前就获得数据，可将有效延迟降至零周期；即使预测失败，也能由正常的访存路径兜底执行。根据该工作的评估，步进预测器（Stride Predictor）能够以较高的准确率覆盖相当比例的装入指令。通过预测装入地址使得装入指令在流水线执行阶段前就完成结果输出，后续依赖指令呈现零周期延迟，避免了流水线气泡。
　　此工作开创了装入指令的访问地址预测的研究方向，是本文设计的重要思想来源。
图2.1　零周期装入的实现示意图
　　综合上述研究[7][12]，访存地址预测器可以按照预测机制分为以下几类：
　　1）上次地址预测器（Last-Address Predictor, LAP）：记录每条装入指令上次执行时的有效地址，预测下次执行时访问相同地址。以 PC 为索引的直接映射表实现，每个表项包含一个地址值。适用于全局变量访问、常量指针解引用、栈上固定偏移访问等地址稳定的场景。Enric Morancho在PACT 1998上提出了分离式的上次地址预测器（Split Last-Address Predictor, SLAP）[13]，通过两张不同的表分类表（Classification Table)和地址表（Address Table），让分类表对每条装入指令做动态的可预测性分类；地址表存放被分类表判断为可预测的装入指令的最近一次有效地址，以此对高可预测性的装入指令进行预测，避免低可预测性的装入指令占用预测表，从而提高了预测表的利用率。
图2.2　分离式的上次地址预测器示意图[13]
　　2）步进地址预测器（Stride Address Predictor, SAP）：检测并记录每条装入指令连续两次执行之间地址的固定差值（即步进值，Stride），预测下次地址为上次地址加步进值。步进地址预测器相比上次地址预测器，能够生成处理器此前从未见过的地址，适用于数组遍历、结构体数组访问等线性地址模式，只需要两次执行就可以学习到步进模式。
　　3）上下文地址预测器（Context-based Address Predictor, CAP）[14]： Michael Bekerman在ISCA 1999提出了上下文地址预测器，通过学习特定上下文（有限有序的历史地址序列）后的地址取值规律，在上下文重复时完成预测，可覆盖任意重复序列，不受线性步长的限制。上下文地址预测器采用两级预测的结构，核心由装入指令缓存（Load Buffer，LB）与链接表（Link Table，LT）构成。装入指令缓存是按静态装入指令（Static Load）索引的表结构，用于为每个静态装入指令维护专属的地址历史与预测元数据；链接表是基于历史上下文索引的预测表，通过存储上下文与目标的基地址的映射关系，完成地址的最终预测。
　　通过以上两个部件，根据装入指令的PC索引装入指令缓存获取地址历史，通过历史索引链接表匹配得到预测基地址，叠加指令偏移生成预测地址，置信校验通过后发起投机访问；装入指令计算出真实地址后，完成预测结果校验，更新装入指令缓存内的地址历史与置信度信息，经防污染规则校验后更新链接表的预测表项。
　　上下文地址预测器的设计空间较大（设计参数包含上下文阶数、上下文表示方式、哈希函数等）且学习时间较长，但能够捕获上次地址预测器和步进地址预测器无法覆盖的非线性重复地址模式，例如多层嵌套循环中的交替访问模式。
图2.3　上下文地址预测器示意图[14]
　　4）混合地址预测器（Hybrid CAP/Stride Predictor）[14]：独立的上下文地址预测器虽能覆盖传统步长预测器无法处理的复杂地址模式，但存在两大核心局限：首先是对于像大数组遍历的长线性的步进访问模式，上下文地址预测器需要维护较长的历史，硬件开销大且冷启动时间长，预测效率低于专用步长预测器；同时，可预测性较差的长地址访问模式易触发上下文地址预测器的历史更新，带来不必要的硬件开销与表项污染风险。而传统步进地址预测器对线性的地址访问模式的预测准确率相当高，但对非线性的地址访问模式基本无效。因此，Michael Bekerman在上下文地址预测器的基础上提出了混合地址预测器。该地址预测器的设计核心是融合上下文地址预测器与步进地址预测器的优势，共享硬件资源，实现全模式地址覆盖，同时平衡预测覆盖率、准确率与硬件开销。混合地址预测器采用了共享的装入指令缓存的融合架构，无需为两个预测器设计独立的索引表，硬件开销更小；混合地址预测器通过一个两位饱和计数器进行动态选择机制对两种预测器进行仲裁：仅当其中一个预测器通过置信度校验时，直接采用该预测器的结果，发起投机访问；而当两个预测器均通过置信度校验时，根据这里两位计数器的状态选择预测结果并发起投机访问；仅当两个预测器均未通过校验时，不发起投机地址的预测，按正常流水线执行装入指令。该规则最大化了预测覆盖率，同时通过置信度机制控制了错误预测率。
图2.4　混合地址预测器示意图[14]
　　在业界中，已经有基于地址预测进行装入指令延迟隐藏的方案投入使用。例如在苹果公司的相关处理器中就使用了Apple Silicon装入地址预测器。近期研究揭示了 Apple M 系列处理器（自 M2 起）中内置了装入地址预测器（Load Address Predictor, LAP）[8]。该装入地址预测器监测同一条装入指令历次执行的地址序列，基于步进模式（Stride）预测其未来将访问的地址，允许处理器在地址计算完成之前投机地发起数据缓存访问。当装入地址预测器预测正确时，装入指令的数据可以在其没有进入装入-存储单元之前就到达寄存器文件，为依赖指令提供了更大的提前量；当装入地址预测器预测错误时，处理器会对投机执行的结果进行回滚。研究表明，装入地址预测器提供了一个较大的投机执行窗口（Speculation Window），使处理器能够在地址确认之前就对投机装入的数据进行计算。这一发现从工业实践的角度验证了装入地址预测技术的有效性和实用性。此外，IBM POWER4 处理器[15]同样采用了激进的装入推测执行策略，是较早在商用处理器中实践装入指令延迟隐藏技术的代表。
　　上述的所有方案都是基于预测方式去推测装入地址，多数都是基于 PC 索引的预测器，都是通过统计历史信息对装入指令的地址进行预测。本文提出的设计方案是以逻辑寄存器号为索引，直接缓存基地址的值，天然地支持不同 PC 的装入指令共享同一基址寄存器的场景（例如结构体的不同字段访问）。同时，本文采用的方案并非对地址进行推测并回滚错误预测的方案，而是对地址提前解析，能保证提前获得的装入地址是一定正确的，不需要进行额外的预测错误处理操作。
　　基于追踪寄存器的提前装入地址解析（Early Load Address Resolution via Register Tracking）[9]采用的也是提前解析的思路，即在进入装入-存储部件之前就提前解析出装入地址，以此跳过部分流水段来降低装入指令延迟。 Bekerman 等人在 ISCA 2000 上提出了一种通过追踪寄存器值来提前解析装入地址的技术。其基本思想是：在发射队列外维护一个寄存器追踪表，记录寄存器值的来源和变化链。当一条装入指令的基址寄存器值可以从追踪表中直接获得时（例如它是另一条已完成的装入指令的结果），该装入指令可以跳过操作数等待阶段直接计算地址。对于可以追踪的变化（如可以跟踪的寄存器间的加法，可以跟踪的寄存器的立即数加法等），在译码阶段进行处理，及时对逻辑寄存器状态进行更新；对于不能跟踪的变化，直接将对应目标寄存器状态置为不可确认的状态。同时针对分支预测错误以及出现异常的场景通过快照方式进行恢复，实现对逻辑寄存器状态的高效以及精准的跟踪。
　　论文设计了三种复杂度和适用场景不同的寄存器跟踪及地址解析方案，均聚焦于跟踪寄存器与立即数进行计算的简单寄存器操作，在解码后到进入装入-存储部件前的流水线阶段完成地址计算，且全程非推测、无需验证和恢复机制，安全性更高：
　　栈指针（ESP）跟踪：主要优化栈的装入指令。因为绝大多数为栈指针的操作都是寄存器加减立即数的形式，只跟踪栈指针寄存器的修改情况可以以较小的开销得到性能提升，使得多数对栈的装入地址可在进入装入-存储部件之前进行解析，是实现最简单的方案。
　　绝对地址跟踪：拓展处理常量地址的装入的场景，仅需在栈指针跟踪机制上支持空的基址，但该拓展功能的相对来说性能增益不显著。
　　基于位移的跟踪（Displacement-based Tracking）：扩展至所有通用寄存器，通过最新寄存器值（LRV）表跟踪寄存器状态，覆盖超80%的装入操作（通过寄存器加立即数的方式进行寻址），较多的此类地址都可以提前进行解析，性能增益最高但硬件复杂度也最大。
　　基于位移的跟踪和本文的方案是较为相似的。该方案首先提出有三类简单的可跟踪的寄存器操作：（1）寄存器加减立即数；（2）寄存器间移动；（3）寄存器的立即数赋值。通过将上述三种类型的操作提前在进入装入-存储部件前执行，提前获得装入地址，就能提前发起访存请求。该方案的核心部件为最近寄存器值表（Latest Register Values，LRV) ，该表是IA32 架构下对逻辑寄存器值一一对应的同步映射表，每个逻辑寄存器对应一个表项。每个表项存储如下信息：

　　对于每个解码后的指令，跟踪器会首先进行可跟踪性校验。如果该指令属于可跟踪的寄存器操作，就会对源寄存器在最近寄存器值表的状态进行检测。如果检测出源寄存器处于未知状态（Unknown），就直接将目的寄存器的有效位置零，并终止本次跟踪；而如果是已知状态，就会读取最近寄存器值表中源寄存器对应的寄存器值，执行指令对应的算术操作，得到目的寄存器的计算结果。
　　如果该指令属于不可跟踪的寄存器操作，就会将该指令的目的寄存器对应的有效位置零，设置为未知状态。同时会将该指令的重排序缓冲器的标号写入表中，并将对应寄存器值字段给置零，用于存储并累积之后的寄存器偏移值的情况。在寄存器处于未知状态的情况下，会继续跟踪后续对该寄存器的可跟踪指令，对于所有的寄存器加减立即数的操作都会累积到寄存器值字段上。当该不可跟踪的指令完成写回后，将该寄存器的结果值转发给最近寄存器值表。最近寄存器值表会根据返回结果值再加上累积的偏移值，得到寄存器的最新正确值，写入寄存器值字段，将有效位置位，恢复正常跟踪状态。如果在这个过程中有新的不可跟踪指令，则会立刻重新刷新寄存器值字段，并将最近不可跟踪指令的重排序缓冲器序号进行更新，后续将以最新的重排序缓冲器序号的指令的结果写回到最近寄存器值表中。
　　该研究表明，利用寄存器追踪技术，相当比例的装入指令可以提前若干周期获得地址。该方案通过跟踪寄存器状态来提前计算装入地址的思路与本文 Tracing Map 的设计理念一致：Tracing Map将每个符合条件能够被跟踪的逻辑寄存器对应的基址缓存在译码阶段可直接访问的Tracing Map表中，实现了对地址的精准计算，用基于基址加上偏移的模式直接提前计算出地址。

　　但本文方案和该论文的方案也存在显著的不同点：
　　1） 原论文方案尽可能追踪了所有能追踪的寄存器的状态，有多个数据来源（装入指令的结果，计算指令的结果都会作为数据来源），且为了尽可能跟踪寄存器的状态增加了各类型的计算逻辑，使得该方案的设计较为复杂。本文的方案主要考虑到步进场景下的访问模式，故总是以装入指令或存储指令的源地址以及能跟踪的立即数加减的结果作为数据来源，且对于计算指令仅跟踪寄存器加减立即数的场景，减少了设计复杂度。
　　2） 原论文方案对不可跟踪状态使用的重排序缓冲器（ROB）的序号作为标识，这使得指令必须在访问完重排序缓冲器之后才能访问最近寄存器值表，在时序上不够友好（在本文的基准方案中，重排序缓冲器的访问是在分发阶段执行的）。本文直接以每个条目的等待序号为索引，每次有新的装入指令触发条目更新时只需要序号加1就能唯一标识该指令，使装入指令不需要等待重排序缓冲器返回序号就可以进行地址提前获取，在时序上对处理器更友好。
　　3） 原论文方案尽管能支持不可跟踪指令对同一逻辑寄存器的进行立即数加减（ADDI指令）情况，但该方案会对所有处于未知状态的寄存器都会进行同样的处理。这会导致即使当前它并没有一个不可跟踪指令在等待返回结果，也会对所有的偏移值进行累积，直到新的不可跟踪指令触发清零。但该行为实际上并无必要性。本文提供的方案能通过判断等待位的方式，支持在既无效又不等待返回数据的情况下，不对寄存器值字段进行修改，减少了不必要的计算和读写寄存器的操作。
　　4） 原论文方案需要对每个分支保存快照，这部分快照的存储开销较大，且需要额外增加快照恢复的逻辑；异常处理也是类似，每次需要把状态还原为逻辑寄存器状态，这会导致处理器需要额外存储逻辑寄存器状态。本文提供的方案直接对出现分支预测错误以及出现异常的场景直接无效表项，设计更为轻量。同时因为引入了等待位，在出现分支预测错误以及异常的情况下，本文方案不会导致不必要的计算和读写寄存器的操作。
　　除了该工作通过追踪寄存器的状态来实现对装入地址的提前解析外，也有一些类似的工作通过追踪寄存器的状态来对装入指令进行加速。
　　Yazdanbakhsh 等人在 ISCA 2024 上提出了 Constable 方案[16]，该方案也是通过跟踪寄存器的状态来安全地消除装入指令，进而提升装入指令的性能。Constable 的核心思想是识别“可能稳定”（Likely-stable）的装入指令，这些装入指令表现为反复从相同地址装入相同数据。如果能安全地消除这些装入指令，避免这些指令的重复执行，就能降低这些装入指令的延迟。Constable 通过较为轻量的硬件结构去追踪每条装入指令的源寄存器（基址寄存器）和目标内存地址是否被修改：只要源寄存器未被写入新值且装入指令的目标地址未被更新，后续的同一基地址寄存器和偏移的装入指令即可被安全清除，直接使用上次缓存的返回值而无需重新发射至存储子系统。它通过三个模块及模块间的交互，实现了上述功能：
　　稳定装入检测器（SLD）：稳定装入检测器是一个基于程序计数器（PC）索引的表，负责识别并验证装入指令的稳定性。每个条目包含最后的装入地址、最后获取的值、稳定性置信度，以及一个消除标志。
　　寄存器监控表（RMT）：寄存器监控表用于追踪源寄存器的修改。该表确认对应寄存器的状态是否被更改，进而确保了重新分配时，没有被标记为可能稳定状态的未完成的装入指令被错误地清除。
　　地址监控表（AMT）：地址监控表用于记录内存中装入指令所访问的物理地址的修改，以避免在地址被写入的情况下错误地清除对应的装入指令。
　　Constable 与本文的Tracing Map方案都是采用了同样的追踪寄存器状态以优化装入指令执行这一设计思路。两者有相同的共识，即装入指令的基址寄存器值在短时间窗口内通常保持不变，并利用这一特性避免了装入指令的完整执行流程。关键差异在于优化的层次和目标：Constable 追踪的是装入指令的完整执行结果，不仅加速地址获取，也加速了数据的访问，最终实现当地址和数据都未变时直接消除装入指令执行；Tracing Map则追踪的是基址寄存器值，用于预测地址并提前发起缓存访问，装入指令仍然需要访问高速缓存获取数据。因此，Constable 适用于地址和数据都高度稳定的装入指令（如全局配置变量的反复读取），而本方案适用于地址可预测但数据可能变化的装入指令（如数组遍历中的顺序访问）。两种技术的目的有所不同，具有互补性。
图2.6　Constable整体方案示意图
　　相比于对装入指令的目标地址提前获取而降低装入指令延迟的方案，另一类方案则是对装入指令或其地址计算相关指令进行优先化调度，通过提前对装入指令进行处理来实现装入指令的提前执行，表现为装入指令的延迟降低。
　　装入指令切片处理器核心（Load Slice Core）方案就是从对装入指令和其地址计算进行优先调度的角度对装入指令进行优化。 Carlson 等人在 ISCA 2015 上提出了装入指令切片核心的微处理器架构[17]。因为装入指令大多数情况都位于长延迟依赖链的根部，提升处理器性能的一个关键点就是加速装入指令的执行。装入指令切片核心在传统乱序执行的处理器核心的基础上增加了一个专用的“装入指令切片（Load Slice）”的旁路流水线，用于识别和优先执行与装入地址计算相关的指令切片（Slice），专门执行装入与存储指令以及地址生成指令。通过将地址计算相关指令从原先完整的乱序执行的核心中分离出来优先处理，装入指令可以更早地获取数据，使得整个执行窗口的有效利用率得到提升。
　　装入指令切片处理器核心的技术核心在于其硬件切片识别算法。该算法通过两个硬件结构协同工作：寄存器依赖表（Register Dependency Table, RDT）追踪每个寄存器最近由哪条指令写入，指令切片表（Instruction Slice Table, IST）以缓存形式存储已识别的后向切片中的指令地址。当一条装入指令在取指阶段时，指令切片表会标记出其地址计算所依赖的所有上游指令如ALU运算、其他装入指令等，这些被标记的指令在主流水线停顿时仍可通过旁路流水线发射执行。整个切片识别过程完全由硬件迭代完成，无需编译器支持或软件重编译。装入指令切片处理器核心以较低的面积开销实现了显著的性能提升。
　　装入指令切片处理器核心的设计理念可以追溯到 Smith在 1982 年提出的解耦访问/执行（Decoupled Access/Execute, DAE）架构[18]概念：通过将处理器的访存操作和计算操作分到不同的流水线中执行，使访问操作可以提前于计算操作运行。后续的前瞻执行（Runahead Execution）[19]也采用了类似的思路，在长延迟缓存缺失期间继续投机地执行指令以产生访存预取效果，进一步隐藏访存延迟。装入指令切片处理器核心可以视为该方案的细化与优化，不是静态地将指令分为访存和计算两类，而是动态地识别与每条装入指令的地址相关的最小指令切片，仅将这些指令分发到旁路流水线中执行。

2.1.2　 指令发射优化
　　在乱序处理器中，提前获取装入地址可以绕过发射队列，这也是一种对指令发射的优化，只不过集中于装入指令。同样而言，发射队列调度策略的优化通过减少装入指令在发射队列中的排队等待时间和资源竞争开销，进而缩短装入指令的有效延迟。两者是从不同层面解决同一问题的互补手段。
　　Alipour 在 HPCA 2020 上提出了延迟-旁路（Delay-and-Bypass，DNB）调度策略[20]，就是一种发射队列调度优化技术。该工作有如下的核心观察：在乱序处理器中，发射队列中的指令可以按照两个正交的维度进行分类，分别是就绪性（Readiness）和关键性（Criticality）。就绪性表示指令的操作数是否已全部就绪；关键性表示指令是否位于程序执行的关键路径上（即该指令的延迟是否直接影响整体执行时间）。传统的发射队列设计对所有指令一视同仁，使用统一的内容寻址存储器（CAM）匹配和优先级仲裁逻辑，导致大量非关键指令占据了宝贵的发射队列的资源，与关键指令（特别是位于长依赖链根部的装入指令）竞争发射端口。
　　延迟-旁路策略提出将这两个维度结合，对指令实施差异化调度：（1）对于操作数已经就绪的指令，如果它不在关键路径上，则绕过复杂的内容寻址存储器匹配发射队列，直接进入一个简单的先入先出（FIFO）的调度结构发射，从而释放发射队列的资源给更需要内容寻址存储器匹配功能的指令，主要是操作数尚未就绪、需要等待唤醒的指令；（2）对于操作数尚未就绪的非关键指令，允许它们在发射队列中被延迟调度而不影响整体性能，为关键指令腾出仲裁的机会。通过这种差异化策略，延迟-旁路策略在仅使用原始发射队列一半深度和宽度的情况下实现了基准乱序处理器的 95% 的性能，同时将调度能耗降低至33%。
　　延迟-旁路策略与本文方案都在发射队列差异化管理这一方向上进行了优化。延迟-旁路策略在发射队列内部进行差异化：识别出非关键或已就绪的指令，将其分流至简单调度结构以进行调度优化。而本文方案则在发射队列外部进行差异化，通过在译码阶段识别出高置信度可预测的装入指令，使其完全绕过发射队列，直接进入装入-存储部件执行。两者都减轻了发射队列的有效负载：延迟-旁路策略将部分非关键指令转移到先入先出队列，本文方案将可预测的装入指令直接从发射队列中移除，两者都使发射队列中剩余的关键指令能够更快获得仲裁机会，减少了发射队列资源的竞争。从装入指令延迟优化的角度看，本文方案通过绕过发射队列，直接消除了可预测的装入指令的发射队列排队延迟；延迟-旁路策略则通过减少发射队列资源的竞争间接降低了所有装入指令（包括不可预测的装入指令）在发射队列中的等待和竞争延迟。

2.2　 存储相关预测技术概述
　　上文的装入地址预测和优先调度技术旨在让装入指令更早地发起缓存访问，但这种激进的提前执行也会引入一个和正确执行相关的副作用问题：存储-装入的内存序违例（Memory Order Violation）。
　　在按程序的原顺序执行的处理器中，每条装入指令总是在其所有前序存储指令完成之后才执行，因此不存在内存序问题。然而，在乱序执行的处理器中，装入指令和存储指令的实际执行顺序可能与程序顺序不同。乱序处理器存在允许装入指令在其前序存储完成之前执行的情况，以提高访存并行度和流水线的利用率。当一条推测执行的装入指令与一条尚未完成地址计算的前序存储指令恰好访问了相同的内存地址时，装入指令此时读取到的将是过时的数据，而非该存储指令即将写入的新值——这就构成了内存序违例。
　　内存序违例的检测与恢复代价通常都是较高的。处理器通常在存储指令完成地址计算后，会检查装入队列（Load Queue）中是否存在已执行但地址冲突的后序装入指令。一旦检测到违例，必须回溯到提交装入指令前的寄存器的状态并重新执行，这会造成严重的性能损失。
　　这一问题对本文的工作尤为相关：Tracing Map使装入指令在译码/分发阶段就获取预测地址并绕过发射队列提前执行，这意味着Tracing Map加速的装入指令比常规路径的装入指令会更早进入装入-存储部件进行执行，在其与前序存储指令之间有更多尚未解析地址的存储指令，从而面临更高的内存序违例风险。因此，有效的存储-装入的内存序违例冲突预测或检测机制是Tracing Map方案性能的重要保障。
　　为了在保证正确性的前提下最大化访存指令的并行度，存储相关预测（Memory Dependence Prediction, MDP）技术应运而生。存储相关预测的核心思想是：利用运行时历史信息预测每条装入是否与某条前序的存储指令存在地址冲突，对预测有冲突的装入指令推迟其执行直到相关的存储指令完成，对预测无冲突的装入指令则允许其提前执行。一个理想的存储相关预测方案应当在两个相互矛盾的目标之间取得平衡：（1）最小化假阳性（False Positive）。即尽可能减小不必要地阻塞实际上没有冲突的装入指令的情况，因为这会降低访存的并行度；（2）最小化假阴性（False Negative）。即尽可能减小允许实际存在冲突的装入提前执行的情况，因为这会导致内存序违例，引入较高代价的恢复开销。
　　 Moshovos 等人在 ISCA 1997 上的开创性工作首次系统地研究了存储-装入（Store-Load）数据依赖的动态预测问题[21]。他们指出，传统乱序处理器对所有装入指令采用盲目推测（Blind Speculation）策略，即总是允许装入指令绕过地址未解析的存储指令执行，出现违例时再进行补救。这种策略在冲突频繁时会导致大量的回滚和重执行，降低处理器效率。Moshovos 等人提出利用运行时历史信息预测存储-装入对之间的依赖关系：对于预测存在依赖的存储-装入对，推迟装入指令的执行直到对应存储指令的地址解析完成；对于预测无依赖的对，允许装入指令提前执行。实验结果表明，该技术能够在几乎消除不必要等待的同时大幅减少内存序违例。
　　 Chrysos 和 Emer在 ISCA 1998 上基于最初的动态预测数据依赖同步的方案，提出了 Store Sets 方案[22]，它已成为最广泛采用的存储相关预测算法之一。Store Sets 的核心思想是：当检测到某条装入指令因为某条存储指令发生内存序违例时，将这两条指令关联到同一个 Store Set 中。此后，属于同一 Store Set 的装入指令将等待其关联的存储指令完成后才执行。Store Sets 使用 SSIT（Store Set Identifier Table）和 LFST（Last Fetched Store Table）两个硬件表实现，以 PC 为索引进行查找。该方案的优势在于简洁高效，且能够自然地处理多对多的存储-装入的依赖关系。因其简单有效，在 Intel 和 AMD 等商用处理器中得到了广泛的工程应用。
图2.9　Store Sets 示意图[22]
　　除了Store Set之外，Load Wait Table也是一种较为常见的方案。 Kessler 在Micro 1999 的文章中详细描述了 Alpha 21264 处理器的存储子系统设计[23]，其中包括一套精巧的存储-装入排序的机制。Alpha 21264 采用了一个 1024 条目的 Load Wait Table（LWT），以装入指令的 PC 低位为索引。当处理器检测到某条装入指令因与先序存储指令发生地址冲突而导致内存序违例时，该装入指令对应的 LWT 表项被标记为需要等待的状态。在后续执行中，如果取指阶段取到一条 PC 命中了 LWT 标记表项的装入指令，该装入指令将被强制等待所有先序存储指令完成地址计算后再执行。这一机制是对让所有装入立即执行的激进策略和让所有装入指令等待所有存储指令的保守策略之间的一种折中，只对历史上发生过违例的装入指令施加等待约束，而大多数不存在冲突的装入指令仍然可以自由地提前执行。然而，LWT 的粒度较粗，该方案仅基于装入指令的 PC 进行预测，不区分与哪条具体存储指令冲突，而这可能引入不必要的等待延迟。Store Sets 正是在 LWT 的基础上做出了改进，通过精确追踪每条装入指令需要等待的具体存储指令，从而避免了过度保守问题。此外，Cain 和 Lipasti提出了基于值的内存排序方法[24]，通过在装入指令提交时直接比较装入数据值是否发生变化来检测违例，提供了一种与上述基于地址预测互补的检测思路。
　　在可扩展性方面，Subramaniam 和 Loh提出了 Store Vectors 方案[25]，用位向量替代传统的基于内容寻址存储器的存储队列搜索来表示存储-装入依赖关系，在保持预测精度的同时显著降低了硬件复杂度，使存储相关预测能够扩展到更大的指令窗口。Sha 等人进一步提出了 NoSQ 方案[26]，彻底取消了传统的存储队列结构，转而通过存储-装入对的预测表和一个简化的存储缓冲区实现存储到装入的数据转发与排序检查，在大幅简化硬件设计的同时保持了与传统方案相当的性能。
　　本文的 SAB（Store Address Buffer）机制与传统存储相关预测技术有着不同的设计思路。传统存储相关预测技术主要基于 PC 历史来预测依赖关系，属于控制流（Control-flow）驱动的预测；而 SAB 利用 Tracing Map 在 Dispatch 阶段已经预测出的装入地址，直接进行地址比较来检测存储-装入的冲突，属于数据流（Data-flow）驱动的检测。SAB 无需额外的预测器训练或历史表维护，其检测结果直接反映了地址层面的实际冲突情况，具有更高的精确度，缓解了假阳性的问题。SAB 与 Tracing Map按照如下方式协同工作来解决存储依赖问题：Tracing Map 为装入指令和存储指令的地址计算都提供地址提前解析的功能，存储指令将提前解析的地址存储在SAB中。在分发阶段利用这些预测地址进行冲突预筛查，对检测到冲突的装入指令推迟其通过加速路径的执行，直到冲突存储指令的地址确认解析完成才能继续执行，从而在利用 Tracing Map 加速装入指令执行的同时控制了内存序违例的增长。
2.3　 依赖指令推测式调度技术概述
　　前两节分别讨论了如何更早地获取装入地址和如何安全地处理存储-装入的内存序违例问题，解决了如何有效地让装入指令更早发射的问题。然而，从装入指令发射到其依赖指令真正开始执行之间，仍然存在一段不可忽视的延迟窗口。为了最大化流水线利用率，推测式调度（Speculative Scheduling）技术通过预测装入指令将按最短延迟（即在转换旁视缓冲器（TLB）命中和高速缓存命中条件下的延迟）完成，在装入指令的数据实际返回之前提前唤醒依赖指令来尝试隐藏这段延迟。如果装入指令实际延迟更长（如高速缓存未命中），已被唤醒的依赖指令需要通过重放（Replay）机制回退重新执行。
　　Kim 等人在论文《Understanding Scheduling Replay Schemes》中对处理器中的推测式调度以及重放机制进行了系统性的分析，研究了不同的重放策略如非选择性重放（Non-Selective Replay）和选择性重放（Selective Replay）对性能和资源利用率的影响，同时提出了新的基于令牌重放的选择性重放方案[27]。该研究表明，推测式调度对于装入指令密集的工作负载至关重要：禁用推测式调度会导致显著的性能下降，因为依赖指令必须等待装入指令执行完成后才会被唤醒。然而，不当的推测式策略也会引发大量不必要的重放，浪费功耗和执行资源。该工作为后续的推测式调度优化提供了全面的基准分析。Fields 等人[28]较早地提出了基于松弛度（Slack）的指令关键性分析框架，为后续差异化调度策略提供了理论基础。
　　Perais 等人在 ISCA 2015 上提出了一种低成本的推测式调度方案[29]。他们观察到：并非所有装入指令的依赖指令都同样关键，实际只有位于关键路径上的依赖指令才真正影响性能。该方案使用一个关键性预测器（Criticality Predictor）来识别出关键装入指令，仅对关键装入指令的依赖指令执行推测式唤醒，而非关键装入指令的依赖指令则延迟到装入指令实际完成后再唤醒。
　　该方案采用的关键度定义如下：若一条装入指令在执行完成时处于重排序缓冲器（ROB）的头部，则该装入指令就处于程序的关键执行路径，其调度延迟将直接影响整体性能；反之则为非关键装入指令，其对整体性能的影响可被忽略。
　　该方案采用局部指令级过滤配合全局行为预测的两级预测结构。指令级局部过滤表主要对单条装入指令的行为进行过滤，由两位饱和计数器预测是否会进行推测式调度，同时由一个静默位判断对该装入指令的调度策略是否是难以预测的。全局行为预测适用于装入指令在对应静默位被置位的情况下，用来预测是否进行推测式调度。这种差异化策略在保持性能的同时大幅减少了不必要的推测和重放开销。
　　同时，该方案通过调度偏移（Schedule Shifting），针对一级高速缓存的组冲突，同一周期发射第二个装入指令时，通过延迟一周期规避冲突问题，以低成本规避了 74.8% 的重放。
图2.10　调度偏移解决组冲突的周期示意图[29]
　　本文方案在推测式唤醒方面主要是在BOOM V3处理器的功能上进行拓展：BOOM V3 处理器原有的推测式唤醒机制仅覆盖从地址生成单元发射到装入-存储部件的装入指令，而由于本文的方案会直接让装入指令在分发阶段进入装入队列中，绕过发射队列的装入指令并不会被推测式唤醒。本文将推测式唤醒扩展至新的路径，使通过本文方案加速的装入指令也能提前唤醒依赖指令，进而实现了从装入指令提前发射到依赖链整体提前执行的完整加速。
2.4　 本章小结
　　本章从装入地址提前获取与指令发射优化、存储依赖预测以及依赖指令推测式调度三个方面系统性地回顾了与装入指令延迟优化相关的代表性工作。这三类工作都旨在减少装入指令对系统整体所带来的延迟，能相互配合提升处理器的执行效率。
　　装入地址提前获取通过提前获得装入地址，让装入指令可以绕过发射等流水段，缩短了装入指令的延迟路径，避免了进入发射队列及其仲裁，读寄存器等开销。装入地址提前获取可分为两种类型：一种是通过对装入地址进行预测，让其能在进入装入-存储部件前就获得装入地址，预测的方式也分确定性和非确定性的方式，确定性预测需要跟踪寄存器状态，逻辑复杂度更高，但提前解析出的装入地址一定无误；非确定性预测能对所有装入指令都进行预测，但有预测错误的风险；另一种通过对装入指令及其相关指令通过旁路流水线进行提前调度，也降低了装入指令的延迟。同时，因为提前获取装入地址可以绕过发射队列，降低了发射队列的负载，也是一种对指令发射的优化。本章对各个部分的相关工作进行论述，阐述了隐藏装入指令的延迟的重要性。
　　存储依赖预测主要缓解存储-装入的内存序违例，降低了装入指令乱序执行所带来的性能损失。本章从 Moshovos 等人的开创性工作出发，经 Store Set、Alpha 21264 的 LWT、Store Vector及 NoSQ等方案，阐述存储依赖预测技术对缓解隐藏装入指令延迟副作用的重要性。
　　在推测式调度方向，本章回顾了重放机制的技术权衡和差异化推测式调度策略，阐述了推测式唤醒扩展至新的路径的重要性。
　　综合来看，现有工作通常聚焦于单一维度的优化。本文提出的方案的独特之处在于将三个维度纳入统一的协同优化框架：Tracing Map在译码阶段预测装入指令和存储指令的目标地址，实现装入指令绕过发射队列的提前执行；SAB 利用Tracing Map提供的存储指令的预测地址在分发阶段进行数据流驱动的冲突检测，控制提前执行带来的内存序违例风险；推测式唤醒扩展覆盖由提前地址解析所带来的新的获得装入地址的路径，使提前执行的装入指令也能推测式唤醒依赖指令，充分释放延迟缩短的性能增益。
第三章　 跟踪基址值的装入指令延迟隐藏机制的设计与实现
　　本章将基于RISC-V开源处理器BOOM V3对跟踪基址值的装入指令延迟隐藏机制进行设计与实现，以此论证该方案在真实的现代处理器设计中的可行性。本章将先对BOOM V3超标量处理器的流水线进行分析，并对装入指令在处理器流水线的执行流程以及装入-存储部件进行详细分析。然后本章将在BOOM V3平台上对基于跟踪基址值的装入指令延迟隐藏机制的设计与实现进行探讨。将访存的地址提前计算、对基地址常数偏移的支持、基于存储地址计算的存储依赖检测以及对依赖延迟隐藏的装入指令的指令提前唤醒机制进行详细分析，并对基于BOOM V3处理器上的实现进行探讨。
3.1　 BOOM V3处理器分析
　　BOOM V3（The Berkeley Out-of-Order Machine V3）处理器是由加州大学伯克利分校研发的一款开源的处理器核[30][31]。该处理器核是一个基于RISC-V指令系统、可综合的且参数化的超标量乱序处理器核。该处理器基于Chisel硬件构造语言[32]开发，构建于Rocket Chip[33]生态之上，具有灵活的参数配置，支持各类型的研究。BOOM V3处理器的微架构设计受 MIPS R10000[34]和 Alpha 21264[23]两款经典乱序处理器的影响较大。与这两款处理器一致，BOOM V3处理器采用统一物理寄存器堆（Unified Physical Register File）设计和显式寄存器重命名（Explicit Register Renaming）的策略，将所有体系结构寄存器和推测性的中间结果统一存储在物理寄存器堆中，通过重命名映射表将逻辑寄存器映射到物理寄存器，解决了 WAR（写后读）和 WAW（写后写）数据冒险的问题。
　　考虑到上述特点，本文基于BOOM V3处理器进行研究。
3.1.1　 BOOM V3流水线分析
　　BOOM V3流水线可分为以下几个阶段：取指（Fetch）、译码（Decode）、寄存器重命名（Register Rename）、分发（Dispatch）、发射（Issue）、读寄存器（Read Register）、执行（Execute）、访存（Memory）、写回（Writeback）以及提交（Commit）。这其中，BOOM V3处理器在设计的时候将寄存器重命名阶段进行了拆分，前部分和译码阶段进行了合并，后部分和分发阶段进行了合并；访存阶段只有访存指令会执行；提交阶段是由重排序缓冲器异步完成的。
　　BOOM V3处理器在每个流水线阶段有如下功能：
　　取指阶段（Fetch）：取指阶段负责从指令高速缓存中获取指令并送入后端流水线。前端模块（Frontend）在每周期完成 PC 选择、访问指令转换旁视缓冲器（I-TLB）以及指令高速缓存（I-Cache）和分支预测查询，根据取指宽度取出一组指令。取指得到的指令与分支预测结果一起进入取指缓冲器（Fetch Buffer），起到前后端解耦缓冲的作用。取指目标队列（Fetch Target Queue, FTQ）记录每个取指包的 PC 和预测元数据，供后端在分支解析时查询和修复。分支预测器采用 TAGE-L 算法[35][36][37]，配合 BTB、RAS 和全局历史修复机制，实现较高精度的分支预测。
　　译码阶段（Decode）：译码阶段从取指缓冲器中取出指令，根据解码宽度使用独立的译码单元（DecodeUnit）并行解析。每个译码单元将 RISC-V 指令映射为内部微指令（MicroOp），确定其功能单元类型、发射队列类型、操作数来源和目标寄存器类型等控制信号。同时，分支掩码生成逻辑为每条分支指令分配一个标签，并为所有指令维护分支掩码，标记其推测路径。当后续资源不足时，译码阶段通过反压信号避免从取指缓冲器中取出指令。
　　重命名阶段（Rename）：重命名阶段消除指令间的假数据依赖（WAR/WAW 冒险），在BOOM V3处理器中通过三个核心结构协同完成：（1）重命名映射表：以逻辑寄存器号为索引，查询源操作数的物理寄存器映射，并为目标寄存器分配新的物理寄存器；（2）空闲列表：管理未被占用的物理寄存器，列表为空时阻塞指令；（3）忙碌位表：标记每个物理寄存器的值是否已就绪，其查询结果附加到微指令的信息中供发射队列使用。BOOM V3处理器会存储映射表的快照（Snapshot），在分支预测错误时通过使用映射表快照恢复正确状态。
　　分发阶段（Dispatch）：分发阶段将重命名后的微指令分配到后端资源：每条指令写入重排序缓冲器（ROB）获得其在重排序缓冲器的序号；装入指令和存储指令分别分配装入队列和存储队列的条目；分发器（Dispatcher）根据在译码阶段获得的微指令信息，将微指令路由到对应的发射队列（访存/整形/浮点）。分发阶段的阻塞条件包括重排序缓冲器满、装入队列或存储队列满、发射队列满和空闲物理寄存器不足等，只要满足任一条件就会进行反压，影响指令分发。
　　发射阶段（Issue）：发射阶段是乱序执行的调度核心。BOOM V3 的发射队列将指令按年龄排序，通过唤醒-选择机制调度就绪指令。唤醒分为三类：（1）快速唤醒：在指令发射的同周期提前广播目标寄存器号，使依赖指令可在下一周期就能立即发射；（2）慢速唤醒：在结果实际写回时广播，主要用于延迟不定的指令；（3）推测式唤醒：在装入发射到装入-存储部件（LSU）时推测其将以数据转换旁视缓冲器（D-TLB）和一级数据高速缓存（L1 D-Cache）命中延迟完成而提前广播，若装入指令未命中则需取消该指令等待重新调度。选择逻辑在就绪指令中按年龄优先级发射。
　　寄存器读取阶段（Register Read）：发射后的指令从物理寄存器堆读取源操作数，或通过旁路网络（Bypass Network）直接获取上一周期可旁路指令（如执行单元）的结果，实现指令链的每周期一条流水化执行。若进入此阶段时装入指令出现了高速缓存未命中且该指令是被推测式唤醒的，那么该指令就会被取消，不进入执行阶段。
　　执行阶段（Execute）：BOOM V3 处理器包含多个执行单元：ALU（1 周期，可旁路）、跳转单元（分支解析与预测错误检测）、乘法/除法单元（乘法为 3 周期，除法延迟不定）以及访存地址计算单元（AGU，计算基地址+偏移得到有效地址后送入装入-存储部件）。浮点计算指令则通过独立的浮点流水线管理浮点计算和除法/开方单元。执行结果通过旁路网络或寄存器堆的写端口返回。
　　访存阶段（Memory）：只有访存指令会执行，且只有装入-存储部件内部会执行。装入-存储部件内部要处理虚实地址转换、数据高速缓存（D-Cache）访问、存储-装入转发和内存序检查等复杂操作。这其中，虚实地址转换发生在执行阶段；数据高速缓存访问和内存序检查发生在访存阶段；存储-装入转发发生在写回阶段。装入-存储部件的详细工作流程将在 3.1.2 节结合装入指令的执行路径展开。
　　写回阶段（Writeback）： BOOM V3 的写回机制是分布式的：整型寄存器堆的写端口由仲裁器管理，仲裁器会对装入-存储部件的装入指令的数据、浮点转换到整数等数据来源进行管理；其余写端口直接与各执行单元连接。写回的同时会通知重排序缓冲器更新指令完成状态，并广播目标寄存器号唤醒发射队列中的依赖指令、清除忙碌位表中的对应位。
　　提交阶段（Commit）：重排序缓冲器按行组织（每行对应一组分发的指令），提交逻辑每周期会检查重排序缓冲器的头部：若头部所有指令均已完成且无异常，则按序提交，释放旧物理寄存器到重命名模块的空闲列表中、通知装入-存储部件提交已确认的存储指令以及更新体系结构状态。若头部指令携带异常，重排序缓冲器会触发流水线冲刷并恢复到正确状态。如果出现了分支预测错误，则在检测后通过分支更新的信号进行通知，重排序缓冲器会据此清除错误预测路径上的所有指令。

3.1.2　 BOOM V3 中装入指令执行流程
　　装入指令是 BOOM V3处理器的流水线中路径最长、涉及子系统最多的指令类型。以下详细分析一条装入指令从取指到提交的完整生命周期。
　　1）取指：装入指令作为取指包的一部分从指令高速缓存中取出，经取指缓冲器排队后进入译码阶段。
　　2）译码：译码单元将装入指令译码为微操作。关键控制信号会有如下的设置：发射队列类型会设置为内存发射队列，路由到内存发射队列；功能单元会设置为使用访存功能单元；同时设置需要装入队列条目、会进行内存读操作信号以及将译码得到的立即数偏移写入对应字段中。
　　3）重命名：重命名阶段为装入指令的目标寄存器分配一个新的物理寄存器，并查询源操作数基址寄存器的当前物理映射。忙碌位表会查询对应物理寄存器是否就绪，如果产生该物理寄存器数据的指令尚未完成执行，会将源寄存器的忙碌位进行置位。
图3.2　BOOM中分发阶段中装入-存储部件的行为
　　4）分发：装入指令的微指令被分发到三个模块中：（1）重排序缓冲器：重排序缓冲器分配条目，并将条目初始化为“未完成”状态。（2）装入队列：装入-存储部件会为该装入指令分配一个装入队列条目。装入队列条目初始化时，会将有效位（valid）置位，并将微指令写入对应表项；已执行（executed）、已成功执行（succeeded）、内存序错误（order fail）、被观察位（observed）以及存储-装入转发位（forward std val）清零，并且根据当前的存储队列的情况记录存储掩码以及存储队列的队尾，其中存储掩码记录当前所有比该装入指令更老且尚未完成地址计算的存储指令的位图，用于后续的存储-装入转发和排序检查；存储队列队尾用于后续判断存储指令是更新的还是更老的指令。（3）内存发射队列（MEM IQ）：微指令进入内存发射队列，等待操作数就绪后发射。
　　5）发射：装入指令在内存发射队列中等待其基址寄存器操作数就绪。一旦通过唤醒机制对应的物理寄存器的忙位被清除，装入指令就会变为可发射状态。发射选择逻辑按年龄优先级选中该装入指令，将其发射到访存执行端口。
　　6）寄存器读取：从物理寄存器堆中读取基址寄存器的值（或通过旁路网络获取）。
　　7）地址计算：位于执行阶段。访存执行单元根据基地址和立即数偏移计算有效地址。计算结果发送给装入-存储部件。
　　装入指令经过上述阶段之后，进入装入-存储部件进行处理。这其中主要有三个阶段，可分为S0、S1、S2阶段。其中S0阶段位于执行阶段；S1阶段为访存阶段；S2阶段为写回阶段。装入-存储部件内部是一条较为独立的流水线，能独立定义处理的访存请求的宽度（Memwidth）等参数。
　　8）S0 阶段：S0阶段的装入-存储部件主要有如下功能：（1）请求信号生成；（2）请求信号仲裁；（3）访问数据转换旁视缓冲器（D-TLB）;（4）将请求发送给数据高速缓存（D-Cache）;（5）结果写入装入队列或存储队列。
　　在地址生成单元计算出的虚拟地址会进入仲裁逻辑。仲裁逻辑会根据四种资源：数据转换旁视缓冲器、数据高速缓存、重排序缓冲器以及内容寻址存储器（CAM）进行仲裁。输入信号按照优先级排序，包括：从地址生成单元进入的装入或存储指令（incoming）、栅栏指令（fence）、缓存行被释放（release）、重试的装入和存储指令（retry，表示需要重新访问数据转换旁视缓冲器）、被唤醒的装入指令（wakeup，因NACK需要重新访问数据高速缓存的装入指令）以及需要提交的存储指令。只要资源没有冲突，请求就可以并行执行。
　　经过仲裁逻辑选择的一条或多条指令会进行执行。如果指令需要访问数据转换旁视缓冲器，就会进入并进行虚实地址转换。数据转换旁视缓冲器会返回物理地址以及访问权限检查结果。如果数据转换旁视缓冲器命中，物理地址在本周期即可用。对于装入指令，由地址生成单元进入和重试的装入指令请求都会按照该路径执行。
　　如果数据转换旁视缓冲器命中且地址是可缓存的（Cacheable），此时会根据仲裁成功的请求是否请求了数据高速缓存，使用物理地址向一级数据高速缓存发起读请求。对于装入指令而言，除了上述两种类型的装入指令请求，还有被唤醒的装入指令也可能会访问数据高速缓存。
　　如果是由地址生成单元进入和重试的装入指令请求，数据转换旁视缓冲器翻译结果和物理地址被写回装入队列对应条目的地址字段，并标记其为物理地址。如果数据转换旁视缓冲器未命中（D-TLB Miss），虚拟地址被写入装入队列的地址字段并标记其为虚拟地址。该装入指令请求会等待转换旁视缓冲器重填，后续通过重试路径重新尝试访问转换旁视缓冲器进行虚实地址转换。
图3.3　BOOM中装入-存储部件的S0阶段行为
　　9）S1 阶段：S1阶段的装入-存储部件主要有以下功能：（1）传递信号给重排序缓冲器；（2）访问存储队列的内容寻址存储器；（3）访问装入队列的内容寻址存储器（4）异常判断及推测式唤醒。
　　存储以及栅栏指令的请求会传递给重排序缓冲器。因为只要存储指令的物理地址和数据都准备好，此时存储指令就可以被提交了。栅栏指令则不需要额外计算数据就可以提交。
图3.4　BOOM中装入-存储部件的S1阶段的重排序缓冲器相关行为
　　装入指令的请求会在该阶段访问存储队列的内容寻址存储器。内容寻址存储器将装入指令的物理地址与所有比它更老的存储队列中的条目（由存储掩码确定）进行地址比较。如果发现存在有地址匹配、地址对齐部分相同且字节掩码完全覆盖装入指令的存储指令，该存储指令的数据就可以直接转发给装入指令。此时内容寻址存储器会向数据高速缓存发送取消信号（kill）取消已发出的数据高速缓存的请求，转而使用存储队列中的存储数据作为装入指令的结果；如果地址匹配但字节掩码部分重叠，装入指令会被阻塞，直到对应的存储指令的数据写入数据高速缓存之后，才能被重新唤醒执行；如果匹配的存储指令的地址有效但数据尚未就绪，装入指令会被阻塞直到存储指令的数据可用。
　　存储指令的请求会在该阶段访问装入队列的内容寻址存储器。当一条存储指令的地址计算完成时，装入队列的内容寻址存储器会搜索装入队列中所有比该存储更新且已执行的装入指令。如果发现了地址冲突，即有更新的装入指令已经以推测方式读取了与该存储指令相同的地址的数据，那么该装入指令对应条目的内存序错误位（order fail）被置位，此时产生了内存序违例。该违例会以微异常（mini exception）的形式报告给核心，触发从该装入指令开始的流水线冲刷和重新执行。
　　除了存储指令的请求，装入指令的请求也会访问装入队列的内容寻址存储器，进行装入-装入顺序的检查。如果一条更新的装入指令已执行且其目标缓存行被外部释放，而较年长的装入指令正在重试，则可能存在可见性问题，需要取消更新的装入指令的结果。此时依旧将该更新的装入指令对应条目的内存序错误位进行置位，产生内存序违例，并进行异常处理。
　　同时，该阶段也会进行异常处理。装入-存储部件中的异常包括之前的执行流程产生的异常（如未对齐异常、权限异常等），以及在内容寻址存储器查找过程中产生内存序错误的异常。异常处理逻辑根据发生异常的指令的重排序缓冲器的序号做一个新旧指令的判断，优先抛出旧指令的异常。
　　该阶段也会对依赖指令进行推测式唤醒。在这个过程中，如果是从地址生成单元进入的指令，则推测式唤醒发射队列中依赖该装入指令数据的指令。如果目标寄存器是0号寄存器则不会进行推测式执行。
图3.5　BOOM中装入-存储部件的S1阶段关于装入及存储队列的行为
　　10）S2 阶段：S2阶段的装入-存储部件主要有以下功能：（1）数据高速缓存的命中处理；（2）数据高速缓存的未命中处理；（3）存储-装入转发的处理；（4）推测式唤醒处理。
　　如果装入指令访问数据高速缓存后命中，返回的数据会通过回复（response）信号传输给装入-存储部件。装入-存储部件根据装入指令的数据类型（整数或者浮点数据类型）和符号扩展要求，将数据格式化后写回寄存器堆。同时，装入队列对应条目的成功执行位（succeeded） 会被置位。对于存储指令，则只用将对应存储队列的表项成功执行位进行置位。
　　如果数据高速缓存未命中，数据高速缓存分配一个缓存缺失状态处理寄存器（MSHR）处理缓存行填充请求，装入指令进入等待状态。如果数据高速缓存拒绝了请求（NACK，例如所有缓存缺失状态处理寄存器都被占用），装入队列条目的已执行位会被清除，该装入指令的请求将在后续通过唤醒路径重新尝试执行。
　　同时，因为数据高速缓存未命中，那么该装入指令执行的推测式唤醒就是无效的，所有被该装入指令推测式唤醒的依赖指令都需要被取消并等待重新调度。具体机制如下：
　　1）发射队列：装入指令的数据高速缓存未命中信号会广播到所有发射队列。持有被该装入指令推测式唤醒标记的已发射指令被取消，其操作数就绪状态回退到未就绪状态。
　　2）寄存器读取阶段：如果被该装入指令推测式唤醒标记的指令已经离开发射队列进入寄存器读取阶段，则被影响的该指令会被取消（kill），阻止其进入执行阶段，等待被重新唤醒。
　　3）装入指令：如上文所述，出现数据高速缓存未命中的装入指令会进入缓存缺失状态处理寄存器等待缓存行填充。填充完成后，数据高速缓存通过唤醒路径通知装入-存储部件，装入-存储部件重新尝试该装入指令的数据高速缓存访问。装入指令完成后的正常写回会再次触发依赖指令的唤醒，只不过该唤醒就不会再是推测式唤醒了。
　　如果在S1阶段判断会进行存储-装入转发，则数据会在本阶段从存储队列中提取。数据会经格式化后写回，并且会将对应装入队列的条目标记为由存储队列的数据转发而得，并写入对应转发的存储队列条目的索引。
图3.6　BOOM中装入-存储部件的S2阶段行为
　　11）提交与释放：当装入指令到达重排序缓冲器的头部且已完成执行并没有异常，重排序缓冲器就会提交该指令。提交后，装入指令的结果会成为体系结构状态的一部分。装入队列对应的条目会随着装入队列的队头指针移动而被释放，其占用的装入队列以及重排序缓冲器等资源就会归还给处理器，同时将其目的寄存器曾经映射的物理寄存器归还给重命名模块的空闲列表。
　　如果装入在提交时出现异常如内存序错误，重排序缓冲器会进行异常处理，冲刷流水线后从该装入指令开始重新取指和执行，以保证内存访问的正确性。
3.2　 BOOM V3处理器上跟踪基址值的装入延迟隐藏机制的设计与实现
　　本节将详细介绍本文提出的跟踪基址值的装入指令延迟隐藏机制的方案。首先阐述方案的顶层设计思想与总体架构，随后按照“实现基础功能，覆盖率扩展，安全性增强，最后收益放大”的递进逻辑，依次介绍四个子模块在 BOOM V3 处理器上的具体实现：Tracing Map核心模块、立即数加减法累积偏移优化、SAB 冲突预检测模块以及推测式唤醒扩展。
3.2.1　 核心观察与理论分析
　　如第二章所分析，装入指令在超标量乱序处理器中的有效延迟可以分解为两个主要分量：发射队列排队延迟（发射端口仲裁以及读寄存器的延迟）和存储子系统访问延迟。在 BOOM V3 的系统中，一条装入指令从进入发射队列到数据写回，即使在最佳情况（操作数立即就绪、无端口竞争、数据转换旁视缓冲器和一级数据高速缓存命中）下也需经历发射、读寄存器、执行、访存、写回共5个周期。如果基址寄存器由一条长延迟指令产生，装入指令在发射队列中的等待时间将进一步增加。
　　本文方案基于以下核心观察：程序中大量装入指令的地址形式为基地址加上偏移的形式，而同一个基址寄存器在短时间窗口内往往指向相同或相近的地址区域。这种现象广泛存在于以下常见程序模式中：
　　1）循环中的数组遍历：循环体内多条装入指令共享同一基址寄存器（数组指针），仅立即数偏移不同；
　　2）结构体字段访问：对同一结构体的不同字段进行连续访问，共享结构体基址；
　　3）栈帧操作：函数局部变量通过栈指针加不同偏移访问；
　　4）全局变量读取：通过全局指针加偏移访问全局数据。
　　如果能在流水线的早期阶段（如译码阶段）利用缓存的基址值直接计算出装入指令的预测地址，装入指令就可以绕过发射队列的排队及仲裁，以及读寄存器的过程，直接发起缓存访问，就能从根本上消除发射队列排队延迟这一延迟分量。
　　以BOOM V3的处理器为基准，我们以理想情况进行分析：BOOM V3处理器开启了推测式唤醒，对于依赖该装入指令的指令会在访存阶段对该指令进行唤醒。对于一条装入指令，它对依赖指令有着如下影响：对同周期进入流水线的依赖指令，该装入指令的延迟会导致其发射延迟三个时钟周期执行；对下一个周期进入流水线的依赖指令，该装入指令的延迟会导致其发射延迟两个时钟周期执行；对下两个周期进入流水线的依赖指令，会延迟该指令一个时钟周期发射；对第三周期及之后的指令不会延迟其发射。
图3.7　BOOM基准实现中的流水线示意图
　　如果装入指令能绕过发射和读寄存器阶段，分发阶段结束就会进入装入-存储部件，直接进入执行阶段进行虚实地址转换并执行后续流程。即使对绕过的路径不进行推测式唤醒，依旧能对后续依赖指令的发射进行优化：对于同周期的依赖指令，在装入指令写回时，会唤醒该指令并发射。对比BOOM V3处理器的基准，同周期的依赖指令的发射会提前一个周期执行；同理，下一个周期和下两个周期的依赖指令都会提前一个周期发射。第三周期及之后的指令的发射延迟保持不变。综上所述，对于同周期及下一个及两个周期的依赖指令都会提前一个周期发射。

　　实际在处理器运行的过程中，发射队列往往因为端口竞争等原因而导致并不能按照理想情况对装入指令进行调度。本方案通过绕过发射队列，既能减少装入指令的延迟，也能缓解发射队列的资源竞争。
3.2.2　 总体方案架构
　　本文方案由四个紧密协作的子模块组成，各自针对装入指令延迟的不同维度进行优化：
　　1）Tracing Map核心模块，用于地址提前解析与发射队列旁路。Tracing Map是一个以逻辑寄存器号为索引的地址预测表。每个条目缓存该寄存器上一次被用作访存指令的基址时的精确基址值。在译码阶段，当一条装入指令的基址寄存器在Tracing Map中命中时，虚拟地址可以直接由缓存的精确基址值加上装入指令的偏移提前解析出来。该装入指令在分发时会绕过发射队列，直接将预测地址写入装入队列，并通过装入-存储单元的重试路径访问数据转换旁视缓冲器进行虚实地址转换，并在后续访问数据高速缓存和内容寻址存储器。
　　2）立即数加减法的累积偏移优化，用于扩展Tracing Map覆盖率。在循环步进访存模式中，基址寄存器通过立即数加法自增后被装入指令作为源地址使用。纯 Tracing Map方案无法处理这种模式，因为立即数加法修改了基址寄存器的值，Tracing Map的对应条目会失效。立即数加减法累积偏移优化在立即数加减法自增（或自减）时不失效Tracing Map的对应表项，而是将偏移量累积到寄存器中，使Tracing Map能够覆盖循环步进模式。
　　3）SAB 模块，用于存储-装入的冲突预检测。Tracing Map使装入指令绕过发射队列提前执行，增加了存储-装入内存序冲突的风险。Store Address Buffer（SAB）是一个位于分发阶段的轻量级流水线缓冲区，缓存近期分发的存储指令的Tracing Map预测地址。当 Tracing Map命中的装入指令与 SAB 中的某条存储指令发生地址冲突时，该装入指令被标记为“存在冲突”，延迟其执行直到冲突的存储指令的地址完成解析之后才会被选择并执行。
　　4）推测式唤醒扩展，用于提升装入指令的提前执行收益。如上小节所描述，基准BOOM V3 的推测式唤醒机制仅覆盖从发射队列发射的装入指令，不覆盖通过重试及唤醒路径执行的装入指令。推测式唤醒扩展将触发范围扩大到重试路径，使被加速的装入指令也能提前唤醒其依赖指令，理想情况下可将下两个周期的指令的延迟再降低一个周期，使得整个依赖链的延迟更低。

　　需要强调的是，Tracing Map方案引入的推测性是有限且可控的。Tracing Map中存储的基址值是装入-存储部件在执行阶段的获得的精确观测值，而非统计模式推测获得的结果。因此只要基址寄存器的值在Tracing Map缓存之后未被其他指令或信号修改，Tracing Map推测的地址就一定是正确的。
　　Tracing Map方案通过以下多层机制确保安全性：
　　1. 寄存器失效机制：任何非立即数加减法的指令修改某逻辑寄存器时（以该逻辑寄存器为目标寄存器），Tracing Map中该寄存器的条目立即失效，并递增序列号以拒绝所有还在执行过程中的过时回写；
　　2. 全局刷新机制：分支预测错误、重排序缓冲器回滚或异常冲刷时，全部Tracing Map条目都会被无效。其它提前解析了地址的装入指令会随分支掩码或冲刷而被清除。该方式确保只对确定的逻辑寄存器的状态进行追踪；
　　3. 序列号防护机制：序列号防护机制防止过时的装入-存储部件的回写覆盖已失效过以及又被新的访存指令设置为等待状态的 Tracing Map条目；
　　4. 正常访存路径：即使通过Tracing Map提前解析出了地址，装入指令仍需要经过完整的虚实地址转换和数据高速缓存访问流程。绕过发射队列的装入指令只需要额外处理非对齐异常（misalign）等由地址生成单元产生的异常即能保证正确性。
3.2.3　 Tracing Map核心模块的设计与实现
　　Tracing Map核心模块是整个方案的基础，负责地址预测，并进而实现发射队列旁路。本节按照数据在流水线中的流向，依次介绍Tracing Map表结构、译码阶段查找、分发阶段旁路、装入-存储部件的重试路径执行、装入-存储部件的回写更新和失效机制。
　　正如上文描述，Tracing Map是以逻辑寄存器号为索引的地址预测表，该表的表项如下：

　　译码阶段，执行Tracing Map查找逻辑，对每条译码得到的装入指令或存储地址计算微指令（STA）进行地址预测：
　　1）候选指令筛选： 并非所有装入指令或存储指令都会进入Tracing Map查找。以下情况被排除：基址寄存器为零寄存器，其值恒为0；保留装入指令（Load Reserved，LR）需严格遵循原子语义，也不会被查表。只有满足筛选条件的指令才进入后续的命中或未命中的判断。
　　2）同周期依赖检测：在超标量处理器中，同一译码周期内可能有多条指令。如果前序的指令修改了当前指令的基址寄存器，且不是立即数加减法的形式，当前指令的 Tracing Map查找就会被阻塞。如果是独立的Tracing Map，则立即数加减法也会让表项无效。
　　3）Tracing Map查找。如果命中：当Tracing Map条目有效且无阻塞条件时，执行以下操作：（1）读取缓存的基址值；（2）计算预测虚拟地址：Vaddr_predict=BaseValue+ImmOffset。对于装入指令，标记地址已就绪，该装入指令在分发时将绕过发射队列；对于存储指令，预测地址供 SAB 使用，但其仍需进入发射队列等待存储数据的操作数就绪；
　　如果未命中，即当Tracing Map条目无效且未处于等待回写状态时，标记该条目为等待回写状态，指令通过正常路径进入发射队列执行，并且会携带该序列号。装入-存储部件完成地址生成后会将计算得到的基址值回写至Tracing Map。如果同一译码周期内已有前序指令对同一寄存器触发了未命中，后序指令不再重复触发，避免多条指令获得相同的序列号。
　　值得注意的是，分支误预测等全局刷新事件不被包含在Tracing Map查找的阻塞条件中。被这些事件杀死的指令已被处理器的分支掩码机制处理，永远不会提交。将全局刷新加入阻塞条件只会不必要地降低同一译码周期内其他有效指令的Tracing Map的命中率。
图3.11　基础的Tracing Map实现
　　分发阶段，Tracing Map命中的装入指令绕过发射队列的分配。当一条装入指令被标记为地址已就绪时，分派器不为其请求发射队列槽位，该指令仅写入重排序缓冲器和装入队列。这一旁路条件同时使得该装入指令不受发射队列满的背压阻塞——即使发射队列已满，Tracing Map命中的装入指令仍然可以被分发。
　　在装入-存储部件内侧，Tracing Map命中的装入指令在进入装入队列时直接写入预测的虚拟地址，将装入队列条目的地址标记为有效，设置虚拟地址位。未命中Tracing Map的装入指令在分派时地址无效，按照普通的装入指令执行路径执行。
　　执行阶段，Tracing Map命中的装入指令通过装入-存储部件的重试路径执行。如上文所述，重试（Retry）路径是 BOOM V3 中装入指令访问数据高速缓存的三条路径之一。该路径原本用于处理数据转换旁视缓冲器未命中后的虚实地址重新转换，从装入队列中选择一条地址有效但仍为虚拟地址的条目，重新进行虚实地址转换和访问数据高速缓存。Tracing Map命中的装入指令在分派时已将预测虚拟地址写入装入队列，恰好满足重试路径的选择条件，因此可以直接复用这一已有路径，无需新增额外的数据高速缓存访问端口。重试路径通过年龄优先编码器按程序的顺序选择最老的满足条件的装入队列条目发射。如上节的时序分析所示，Tracing Map命中的装入指令经此路径从分发到写回仅需4个周期。
　　当装入指令或存储指令在装入-存储部件中完成地址生成后，该指令在译码阶段被标记为Tracing Map未命中且未处于等待被回写的状态，装入-存储部件会将计算得到的基址值回写给Tracing Map。回写前需检查该指令是否已被分支误预测或流水线冲刷杀死，避免被杀死的指令的过时结果污染Tracing Map。同时，接收回写时还需执行严格的序列号匹配验证：只有当回写携带的序列号与Tracing Map条目当前的序列号完全一致时，回写才被接受。这一机制避免了无效指令回写的问题：当一个寄存器的Tracing Map条目在装入-存储部件执行期间被失效并重新分配后，先前的过时回写因序列号不匹配而被自动拒绝，无需显式地取消这些在途的请求。

3.2.4　 立即数加减累积偏移优化的设计与实现
　　该优化主要用于扩展Tracing Map覆盖率。程序中极为常见的循环步进访存模式如下：
图3.13　循环步进访存模式示意图
　　在基础Tracing Map实现中，立即数加减修改了目的寄存器的值，导致Tracing Map的对应条目被失效。下一次循环迭代中的装入指令会发现未命中，无法利用地址提前解析。这严重限制了其覆盖率。
　　因此，立即数加减累积偏移对这样的场景进行了优化：当检测到立即数加减形式的指令时，不选择失效Tracing Map的条目，而是将对应立即数偏移量累积到基址值的寄存器中，后续装入指令在回写时地址加上累积偏移作为新的基址。这一设计复用了已有的缓存基址字段进行偏移累积，无需为偏移值单独分配存储空间。
　　在该方案中，缓存基址值字段有了新的功能：在等待回写状态时，被复用为偏移累积器。在进入等待回写状态时清零，立即数偏移直接累积于其中；当装入-存储部件回写基址时，将基址与累积偏移相加得到最终基址。
　　同时，因为在RISC-V指令系统中，寄存器间移动语义可等效化为立即数为0的不同寄存器间的立即数加法指令，本方案也同样支持了该语义，并考虑到了RISC-V指令系统中的特例：如果使用了普通加法指令但源寄存器有0号寄存器（该寄存器值恒为0），依旧等效于寄存器移动语义。这进一步拓展了跟踪寄存器值的覆盖范围。
　　在超标量处理器中，同一周期内可能出现对同一寄存器的立即数加法（自增）和以该寄存器为源寄存器的装入指令分别位于前后的情况。由于寄存器的写入要到下一周期才可见，故需要实现同周期转发的逻辑。
　　同周期转发链采用组合逻辑，对于每条指令和每个逻辑寄存器，维护从第一条指令到当前指令之间所有立即数加法自增偏移的累积值。每个槽位在查找Tracing Map时将该累积和加入预测地址计算。考虑到时序和逻辑复杂度的要求，这里采用的累积立即数偏移仅最多能容纳一个前序指令。如果在较大发射宽度的场景出现对同一寄存器超过一个的立即数加减法，则直接将对应条目置为无效并将缓存基址值字段置为0。
　　此外，还需处理同周期转发的边界情况：如果同周期内前序槽位的访存指令访问了无效且未处于等待回写状态的寄存器（此时会将该寄存器设置为等待回写状态），后序槽位的立即数加法需要通过组合逻辑检测到这一事件，从而知道该寄存器要开始被跟踪了，并开始累积偏移。
图3.14　增加了立即数加减偏移功能的Tracing Map实现示意图
　　对于非同一寄存器的立即数加减的同周期转发，当前实现采用保守策略：如果同周期前序指令包含一条对非同一寄存器的立即数加减修改了当前装入指令的基址寄存器，该装入指令的Tracing Map查找被阻塞，回退到正常发射队列路径。对非同一寄存器的立即数加减对目标寄存器的Tracing Map更新在当前周期末写入对应条目，下一周期的指令即可使用。

　　同时，由于在Tracing Map的基础上新支持了立即数加减的功能，这使得在原先的数据更新源上又多了新的数据更新源。同时考虑到超标量的场景，情况就会变得较为复杂。考虑有五种会更新缓存基址值字段值的来源：因异常或分支预测错误等导致的所有寄存器失效、不可跟踪写入导致的目标寄存器失效、装入-存储部件回写源寄存器的值、立即数加减修改的目标寄存器的值以及等待回写状态立即数加减修改的相同寄存器值。
　　其优先级应该按照如下排序：
　　1）因异常或分支预测错误等导致的所有寄存器失效优先级最高。异常或分支预测错误导致所有逻辑寄存器的状态都无法跟踪。默认所有条目的都无效是保守但实现简单且绝对正确的方案。
　　2）不可跟踪写入导致的目标寄存器失效的优先级次之。类似加法或装入指令等修改目的寄存器的指令也会导致寄存器的状态无法跟踪，需要将该条目无效。
　　3）立即数加减修改的目标寄存器的值优先级排第三。立即数加减修改的目标寄存器的值是指令最新的对目标寄存器值的修改，且能够被跟踪，故将该条目置为有效，且将这个目标值写入到缓存基址值字段。
　　4）装入-存储部件回写源寄存器的值的优先级排第四。相比立即数加减修改的目标寄存器的值，回写源寄存器的值因为其实际上跟踪的寄存器状态更早，其优先级应比立即数加减修改的优先级更低。
　　5）等待回写状态立即数加减修改的相同寄存器值的优先级最低。它只跟踪在等待状态期间的偏移累积的情况，相比准确跟踪的寄存器值，优先级更低。
3.2.5　 存储-装入冲突检测的设计与实现
　　Tracing Map使装入指令可以绕过发射队列提前执行，但这改变了装入指令与同程序中先序的存储指令的相对执行顺序。提前执行的装入指令可能在某条先序存储指令的地址尚未计算出时就已经访问了存储子系统。同时，如果两条指令访问了相同的地址，就会发生存储-装入的内存序违例，触发微异常恢复。而这严重抵消了Tracing Map的延迟节省收益。
　　本文在Tracing Map的基础上提出了SAB（Store Address Buffer）。通过在分发阶段预检测潜在的存储-装入冲突，从根源上减少内存序违例异常的发生。SAB 采用移位寄存器流水线结构，每周期将新分发的存储指令预测地址写入流水线头部，旧条目依次移位，最末级自然丢弃。相比环形缓冲区，移位寄存器无需头尾指针或年龄计数器，硬件实现更简洁。
　　SAB默认配置下，每级存储发射宽度数量的存储指令目标地址条目。每条目包含有效位（1 bit）、按字对齐的虚拟地址（38 bit）和存储队列的索引（4 bit）。默认配置下 SAB 为 4 级深度。深度参数可调整，每级存储的存储指令目标地址条目数量也可调整。当出现发射数量的Tracing Map命中的存储指令大于每级存储的数量时，放弃存储后续的存储指令的地址。
　　由于超标量处理器会在一个周期发射多条指令，需要进行同周期冲突检测。当同一分发周期内前序的Tracing Map命中的存储指令的地址与后序的Tracing Map命中的装入指令的地址匹配时，就认为检测到同周期冲突。本方案对同周期的冲突采用的处理方式为降级：直接清除该装入指令的Tracing Map命中标记，使其回到正常的发射队列路径。
　　采用该同周期冲突检测方案的原因是：由上文的分发阶段可知，如果要获取存储队列的序号，就必须要先访问存储队列。如果要获取同周期的存储指令的存储队列序号，就需要先等待存储指令访问存储队列并返回存储队列序号再写入装入队列，这对分发逻辑的改动较大，且时序压力会大很多（要访问两次装入-存储队列）。相比而言，降级处理是一种保守但简洁的设计选择。
　　SAB寄存器中存储的数据主要用于跨周期的冲突检测。 将Tracing Map命中的装入指令的预测地址与 SAB 所有寄存器级中的有效条目进行并行比较。如果发现匹配，该装入指令会被标记为存在冲突，同时记录冲突存储指令的存储队列索引。当多条存储指令匹配时，选择最新的匹配条目。
　　标记了冲突的装入指令仍然绕过发射队列进入装入队列，装入队列需要新增一个表项为依赖存储队列表项（Depend STQ Index），存储该装入指令依赖的存储指令对应的存储队列序号（并需要Invalid状态，表示当前装入指令不依赖任何存储指令）。在重试路径中候选装入指令会被加以限制：只有当存储队列表项对应的冲突存储指令的存储队列条目已被释放，或者冲突的存储指令的物理地址已经完成翻译后，该装入指令才能被选择并允许发射。
图3.16　增加了SAB功能的重试选择逻辑示意图
　　Tracing Map命中的存储指令在访问存储队列后获得存储队列序号。该序号会回写到SAB中，并标记对应条目有效。条目通过移位寄存器流水线每周期向下移动，直到参数设定的流水深度后，被自然放弃。
　　SAB的实现方案能在一定时间窗口内，阻止与Tracing Map命中的存储指令具有相同虚拟地址的装入指令提前发射，相比以PC为索引的控制流预测方案能较大程度缓解假阳性问题。
　　与Tracing Map一致，SAB 在分支预测错误、重排序缓冲器回滚、出现异常以及流水线冲刷时清除所有有效位。

3.2.6　 推测式唤醒扩展的设计与实现
　　如上文所述，BOOM V3 处理器自带有推测式唤醒机制。通过对从地址生成单元进入到装入-存储部件的装入指令在访问数据高速缓存时提前广播其目标寄存器号，使依赖指令可以在装入指令的数据写回之前就被唤醒和发射。然而，Tracing Map加速的装入指令绕过了发射队列，通过重试路径被执行，不会触发推测式唤醒。这意味着Tracing Map加速的装入指令的数据虽然提前到达了寄存器堆，但其依赖指令仍需等到数据实际写回时的标准唤醒才能被发射，导致延迟缩短的收益变小，进而影响到下游依赖链。由上文理论分析可知，在理想情况下，同周期和下一周期的依赖指令的发射会比开启推测式执行唤醒的情况延迟一周期。
　　推测式唤醒扩展的修改复用了BOOM V3 处理器自带的推测式唤醒的方案。其核心修改是将重试路径的发射信号加入推测式唤醒的触发条件。在原始 BOOM V3 中，推测式唤醒仅由从地址生成单元进入装入-存储部件的路径触发；扩展后，重试路径的装入指令发射也会触发推测式唤醒。考虑到本方案基于 MediumBoom 配置进行设计，该配置下从地址生成单元进入装入-存储部件的路径和重试路径共享同一个转换旁视缓冲器和高速缓存端口（由仲裁逻辑确定），两者在同一周期内能实现互斥，因此可以安全地共享推测式唤醒逻辑。
　　推测式唤醒基于装入将在下一周期成功写回的乐观假设。当重试路径的装入指令未能按预期完成（如数据高速缓存未命中）时，已被推测式唤醒的依赖指令通过 BOOM V3 原有的推测失败处理机制被取消和重新调度。具体而言，装入-存储部件在推测式唤醒的下一周期检查数据高速缓存的响应，如果装入指令未成功完成，发射队列中持有推测式标记的已发射指令就被取消，操作数就绪状态回退；已离开发射队列进入寄存器读取阶段的推测执行的指令也会被拦截。本方案仅扩展了触发范围，无需修改任何已有的恢复逻辑。最终实现方案如图3.18所示：

3.3　 本章小结
　　本章围绕降低超标量乱序处理器中装入指令的有效延迟这一目标，首先深入分析了BOOM V3处理器的微架构特征和装入指令的完整执行流程，揭示了延迟瓶颈的来源；在此基础上，提出并详细介绍了Tracing Map地址预测方案的设计思想与四个子模块的实现细节。
　　通过对 BOOM V3处理器的系统性分析，梳理了装入指令从取指到提交的完整生命周期，识别出装入指令的发射队列排队延迟可通过译码阶段地址预测消除、重试（Retry）路径可低成本复用、推测式唤醒可扩展至重试路径、存储-装入冲突是装入指令提前执行的主要风险等关键特征。
　　基于上述架构分析，本文提出了由四个紧密协作子模块组成的Tracing Map方案，以基础功能、覆盖率扩展、安全性增强以及收益放大作为递进架构。Tracing Map核心模块在译码阶段通过寄存器索引的地址跟踪表实现发射队列旁路；立即数加减偏移融合将立即数偏移直接累积到缓存基址字段并支持非相同寄存器间的立即数加减与寄存器移动指令的传播，扩大了可覆盖的程序模式范围；SAB 冲突预检测模块通过移位寄存器流水线在分派阶段预判存储-装入冲突；推测式唤醒扩展将重试路径纳入触发条件，提高了延迟缩短的收益。
　　方案所有逻辑集中在译码和分派阶段以及装入-存储部件的条目选择及推测唤醒的逻辑，不修改处理器核心和存储子系统的核心数据通路。本文方案的核心优势在于其确定性预测的特性，基于精确缓存的基址值而非统计推测，命中时预测结果一定正确，没有预测错误的恢复开销。同时具备无训练开销的特点。

4.1.2　 Verilator 周期精确仿真环境
　　功能验证的主要手段是基于 Verilator[39]的周期精确仿真。Verilator 是一款开源的 Verilog/SystemVerilog 仿真器，其工作原理是将 RTL 设计编译为优化的 C++ 模型，相比传统的事件驱动仿真器（如 VCS、ModelSim），在纯功能验证和长程序仿真场景下具有显著的速度优势。
　　仿真流程如下：Chipyard 构建系统首先通过 FIRRTL 编译器[40]将 Chisel设计转换为 Verilog RTL，随后调用 Verilator 将 RTL 编译为 C++ 可执行的仿真二进制文件。该仿真器加载 RISC-V ELF格式的测试程序，在周期精确的模拟环境中执行，支持打印等方式调试输出和波形生成。仿真过程中通过性能计数器采集 IPC、微异常次数以及本方案相关的性能指标等指标。
　　Verilator 仿真环境的主要优势在于：（1）周期精确，仿真结果与真实硬件行为完全一致（在 RTL 层面）；（2）支持长程序仿真，可运行完整的基准测试；（3）便于插入调试逻辑和性能计数器，无需 FPGA 综合即可快速迭代设计。其主要局限是仿真速度较真实硬件慢数个数量级（典型速度约 10–100 kHz），长程序仿真耗时较长。
4.1.3　 FPGA 硬件原型验证平台
　　为验证设计在真实硬件上的功能正确性和时序收敛性，本文还采用了 FPGA 硬件原型验证。FPGA 平台的硬件和软件环境如下：
　　FPGA开发板：实验采用 Digilent Genesys2 开发板[41]，搭载 Xilinx Kintex-7 系列 FPGA 芯片（XC7K325T-2FFG900C）。Kintex-7 325T 提供约 326K 逻辑单元、840 个 DSP48 Slice 和 16 MB Block RAM，具备承载 MediumBoom 配置（包含本文方案扩展）的完整SoC的资源容量。Genesys2 板载 1GB DDR3 SDRAM 作为主存，通过 MIG 控制器接入 SoC 的 TileLink 总线；此外提供 UART、SD 卡、以太网等外设接口，可支持操作系统级的软件运行。
　　综合工具：FPGA 综合与实现采用 Xilinx Vivado 设计套件[42]。Chipyard 框架集成了 FPGA 构建流程，可自动生成包含处理器核心、总线互连、存储控制器和外设控制器在内的完整 SoC 顶层设计，并调用 Vivado 完成综合、布局布线和比特流生成。生成的比特流通过 JTAG 接口下载到 FPGA 芯片中运行。
　　运行方式：FPGA 原型上的软件加载通过 SD 卡完成。操作系统级验证通过 OpenSBI[43] + Linux 内核[44]引导，经由 UART 串口交互。FPGA 原型的运行频率通常为 50–100 MHz，可在秒级时间内完成 Verilator 仿真需要数小时的测试程序，是验证长程序正确性和调试硬件时序问题的重要手段。
4.2　 功能正确性验证
　　在进行性能评测之前，必须首先确认本文方案的引入不会破坏处理器的功能正确性。功能验证的核心目标是证明：在所有测试场景下，修改后的处理器与基线 BOOM V3 产生完全一致的程序可见行为（寄存器状态、内存状态和 I/O 输出）。
　　功能验证采用分层递进策略，从简单裸机程序到复杂系统软件逐步提升验证覆盖度：
　　1.  ISA 合规性测试：运行 RISC-V 官方ISA测试套件（riscv-tests）[45]，覆盖 RV64GC 指令系统的每条指令的基本功能，验证本文方案的修改未破坏指令执行的正确性。
　　2. 裸机基准程序：运行 dhrystone[46]、qsort、median 等经典裸机基准程序，这些程序包含整数运算、排序算法、函数调用等典型计算模式，验证指令流在复杂控制流和数据依赖下的正确执行。
　　3. 代理内核引导：通过 RISC-V 代理内核（RISC-V Proxy Kernel，riscv-pk）[47]引导执行用户态程序，验证特权级切换、系统调用、虚拟内存管理等操作系统基础功能的正确性。riscv-pk 内部实现了页表管理、陷阱处理和系统调用代理，对处理器的特权态行为进行了较为全面的测试。
　　4. 操作系统级验证：在 FPGA 平台上通过 OpenSBI 固件引导 Linux 内核启动，验证完整的多特权级切换、中断处理、虚拟内存和设备驱动等功能。Linux 内核的启动过程涉及数亿条指令的执行，是对处理器功能正确性最为严格的压力测试。
　　针对每层策略的验证结果：
　　ISA 测试：RISC-V 官方 ISA 测试套件中 RV64GC 相关的全部测试用例在 Verilator 仿真环境下均通过，测试结果与基线 BOOM V3 完全一致。这表明本文方案的引入未影响任何指令的执行语义。
　　裸机基准程序：dhrystone、qsort、median 等裸机基准程序在 Verilator 仿真和 FPGA 硬件平台上均成功运行，程序输出与基线版本完全一致。
　　riscv-pk引导： 通过 riscv-pk 代理内核成功引导并执行了上述裸机程序以及额外的用户态测试程序。riscv-pk 在启动过程中执行页表建立、特权级切换和系统调用处理，所有流程均正常完成，无异常或陷阱错误。
　　Linux 启动：在 FPGA 平台上，修改后的处理器成功通过 OpenSBI 固件引导 Linux 内核，完成内核初始化、设备树解析、根文件系统挂载，并进入 shell 交互环境。Linux 启动过程涉及数亿条指令的执行，包含密集的特权级切换、中断处理和 I/O 操作，是对处理器整体功能正确性最严格的端到端验证。启动过程中本文方案的调试输出显示方案按预期工作。

4.3.2　 SimPoint 采样方法
　　SPEC CPU的基准程序规模庞大，单个程序的完整执行通常涉及数千亿条指令。在周期精确仿真环境及实际运行情况下，完整模拟一个程序可能需要数周乃至数月的时间，这在实际研究中是不可行的。
　　为解决这一问题，本文采用 SimPoint[49]采样方法论对基准程序进行代表性片段提取。SimPoint 的核心思想是：程序的动态执行行为在时间维度上会呈现出阶段性，表现为程序会在不同的执行阶段之间交替，每个阶段内部的微架构行为（如 IPC、缓存命中率、分支预测准确率等）较为稳定。SimPoint 通过以下步骤选取代表性片段：
　　1. 基本块向量（Basic Block Vector, BBV）分析：将程序的动态指令流按固定长度划分为若干区间，对每个区间统计基本块的执行频率，构成该区间的 BBV 特征向量。
　　2. 聚类分析：使用 K-means 等聚类算法对所有区间的 BBV 进行聚类，将行为相似的区间归为同一阶段。
　　3. 代表性区间选取：从每个聚类中选取距聚类中心最近的区间作为该阶段的代表性片段（SimPoint），并记录该聚类的权重（所含区间数占总区间数的比例）。
　　本实验中，每个基准程序选取权重最大的 SimPoint 片段进行仿真。每个 SimPoint 的仿真长度为 12 亿条指令，前10 亿条指令作为预热阶段，用于填充缓存、分支预测器和Tracing Map等微架构状态，使其达到稳态；后2亿条指令为正式测量阶段，在此期间采集性能计数器数据。预热阶段的引入确保了测量结果不会受冷启动效应的影响。
　　SimPoint 方法论的有效性已在大量体系结构研究中得到验证：使用少数代表性片段即可以极小的仿真时间开销，获得与完整程序执行高度一致的性能特征。这使得在资源受限环境下对总计 20 个 SPEC CPU 2006 和SPEC CPU 2017基准程序的全面评测成为可能。
4.3.3　 硬件性能计数器
　　性能评测的数据采集依赖于在 BOOM V3 处理器上扩展实现的硬件性能计数器（Hardware Performance Monitor, HPM）。RISC-V规范中定义了标准的 CSR 性能计数器接口，但其可用计数器数量有限且缺乏灵活的采样控制机制。为满足本文方案评测中对细粒度微架构事件统计的需求，本文基于开源的 BOOM 性能计数器扩展框架BOOM-stop[50]进行了定制化实现。
　　除了常规的统计信息，本文对本方案相关的关键统计信息进行了扩展，包括Tracing Map快速地址转换命中次数、SAB冲突检测次数以及推测式唤醒相关统计等。这些事件为深入剖析本方案的各子模块的行为特征提供了直接的硬件级观测手段。
　　该框架通过复用 RISC-V 指令系统的立即数加法指令实现对计数器的软件控制。处理器将这类指令识别为特殊的计数器操作命令，根据立即数的取值执行不同的控制功能，如计数器复位、计数器读取、计数器使能控制、统计权限级别等功能。这一控制机制完全在硬件层面实现，无需修改处理器的特权模式或中断处理逻辑，且对正常指令流的执行不产生任何性能开销。
　　基于上述基础设施，性能数据的采集流程如下：SimPoint 检查点加载后，测试程序首先通过控制指令设置进程标记、指令预热和统计权限级别。程序执行过程中，计数器在预热阶段结束时自动复位，随后在测量阶段内持续累加。测量阶段结束后，程序通过计数器读取指令依次读出所有计数器的值，并将结果输出至日志文件。分析脚本解析各基准程序的日志，计算 IPC等指标，并生成对比图表。
4.3.4　 性能评测指标
　　本文采用以下指标评估本文方案的性能效果：
　　1）每周期指令数（Instructions Per Cycle，IPC）。IPC是衡量处理器执行效率的核心指标，定义为测量期间提交的指令总数与消耗的时钟周期总数之比：
　　IPC=  提交指令数/时钟周期数
　　IPC 越高表示处理器在单位时间内完成的有效工作越多。对于超标量乱序处理器，IPC 综合反映了流水线利用率、缓存命中率、分支预测准确率等多种因素的共同效果。为了获得跨越多个基准程序的整体性能评估，本文采用几何平均值作为汇总指标。相比算术平均值，几何平均值对异常值（特别高或特别低的 IPC）更为稳定，且满足性能比值的一致性要求[51]。
　　2）加速装入指令比例（Accelerated Load Ratio，ALR）。ALR衡量通过本文方案能加速的装入指令的覆盖程度。定义为Tracing Map命中且分发的装入指令和提交的装入指令数之比：
　　ALR=  (Tracing Map命中装入指令数)/提交装入指令数
　　3）加速装入指令的推测式唤醒比例（Accelerated Load Speculative Wakeup Ratio，ALSWR）。 该指标主要衡量加速的装入指令的进行推测式唤醒的出现次数。定义为加速装入指令的推测式唤醒次数与总推测式唤醒次数之比：
　　ALSWR=  加速装入指令的推测式唤醒次数/总推测式唤醒次数
　　除了上述指标之外，还需要统计并分析内存序违例触发的微异常的变化情况、数据转换旁视缓冲器的未命中率变化情况、数据高速缓存未命中率变化情况等指标。这些指标的组合分析可以揭示不同基准程序下本文方案性能表现差异的底层原因。其中，内存序违例触发情况和基线情况比较可以观察到Tracing Map以及立即数偏移加速对内存序违例产生的影响，同时也能比较得出SAB对内存序违例的缓解效果；数据转换旁视缓冲器及数据高速缓存所属的相关数据则主要是分析本文方案对存储子系统所带来的影响。
　　同时，还需要分析本文方案的成本开销。本文将根据综合工具报告，统计并分析每种方案的硬件资源使用量的情况。

4.4　 性能评测结果及分析
　　本节将基于上节所定义的评测方案，将对应各配置下的比特流烧录到FPGA开发板上运行，采集各配置在SPEC CPU 2006和SPEC CPU 2017共20个基准程序的性能数据，并对运行结果进行系统分析。
4.4.1　 IPC分析
　　从 IPC 的几何平均值来看，四个优化配置在 SPEC CPU 2006 和SPEC CPU 2017的20个基准程序上相对于基线分别实现了1.27%、1.65%、2.25%和2.85%的IPC性能提升。这一递进趋势表明每个子模块均贡献了正向的性能增益，且各模块之间具有良好的累积效果。
图4.1　各配置下IPC变化情况
　　这其中， astar（提升9.53%）、bzip2（提升9.94%）和 dealII（提升6.93%）是完整方案下获益最大的三个程序。astar 和 bzip2 在各模块递进添加过程中几乎都表现出持续的性能提升。同时，perlbench（提升3.72%）、blender（提升3.22%）、deepsjeng（提升2.87%）、lbm（提升2.77%）等程序也获得了较稳定的性能提升。这说明Tracing Map模块、立即数偏移融合、SAB冲突预检测和推测式唤醒扩展对这类程序均有正向贡献。20个程序在完整方案下全部获得正向收益，说明本文方案具有良好的普适性。
　　这其中，h264ref 的变化路径尤为值得关注。仅有Tracing Map时性能反而下降3.94%，但随着SAB和推测式唤醒的引入逐步恢复并最终实现+2.28%的正收益，体现了三个功能模块对基本功能的有效补偿。类似地，SPEC CPU 2017中的mcf（从−0.97%恢复至+1.71%）和leela（从−1.02%恢复至+0.98%）也展现出SAB的冲突拦截效果。
4.4.2　 加速装入指令比例分析
　　加速装入指令比例是体现Tracing Map覆盖率的核心指标。在性能测试中，立即数偏移融合将Tracing Map的总体平均覆盖率从 27.29% 提升至 44.47%。这一结果验证了在上一章中关于循环步进模式下基址寄存器以立即数步长递增的设计假设。立即数偏移融合通过跟踪累积的偏移值，使得Tracing Map表项在循环体内持续有效，而非在每次出现了立即数加减更新后失效。
图4.2　各配置下加速装入指令比例变化情况
　　这其中，xalancbmk（提升52.19%）和 leslie3d（提升33.33%）的立即数偏移融合的贡献尤为突出。xalancbmk 的 XML 文档处理涉及大量的树节点遍历，内层循环以指针步进方式访问连续存储节点，立即数偏移融合使得Tracing Map表项在遍历过程中持续有效。leslie3d的大涡模拟计算以固定步长遍历三维数组，立即数偏移融合贡献了绝大部分覆盖率。
　　而cactuBSSN（仅提升0.02%）的覆盖率在无立即数偏移融合时已达63.86%，说明其大部分装入指令的基址在程序执行过程中保持不变，无需立即数偏移融合进行补偿。同时，cactuBSSN无论是否增加立即数偏移功能，Tracing Map的覆盖率都较高且几乎不变，说明该程序的访存模式以固定基址的非自增模式为主。
　　从Tracing Map表项更新次数的角度可以进一步揭示立即数偏移融合提升覆盖率的内在机制。在仅有基础Tracing Map的配置下，表项更新完全来自装入-存储部件的回写：当一条装入指令未命中Tracing Map时触发等待，待装入-存储部件完成地址计算后将基址回写，表项才变为有效。因此在基础配置下，每次循环迭代中基址寄存器被立即数加法修改后表项就会失效，下一次迭代的装入指令必须再次经过完整的访存流水线才能重新建立有效表项。这意味着表项在有效、失效、等待回写再到有效的循环中反复切换，实际处于有效状态的时间窗口较短，能够被加速的装入指令比例因此受限。
　　启用立即数偏移融合后，立即数加法不再使表项失效，而是将偏移累积到缓存基址字段中，表项在循环步进过程中持续保持有效。这一变化的直接体现是：装入-存储部件的回写更新次数从平均每程序约1041万次下降至约825万次，降幅约20.8%，表项不再因立即数加法而频繁失效和重建，回写需求自然减少。与此同时，新增的立即数偏移更新平均每程序约894万次，表项的总更新次数从约1041万次增至约1718万次。总更新次数的增加恰恰说明了表项在更长的时间窗口内保持有效：在基础配置下这些立即数加法事件会使表项失效，而在偏移融合配置下则被转化为轻量级的偏移累积操作，表项在整个循环执行过程中持续可用。这正是覆盖率从27.29%提升至44.47%的根本原因。同时，立即数偏移更新仅涉及译码阶段的累加操作，硬件开销低于需要完整访存流水线执行的装入-存储部件回写更新。
　　从各程序的特征来看，leslie3d的装入回写更新从1207万次大幅下降至485万次（降幅59.8%），而立即数偏移更新高达2568万次，说明该程序的大涡模拟计算中几乎所有基址寄存器的变化都是固定步长的立即数自增，偏移融合使得表项在大量迭代中持续有效，覆盖率因此从3.90%跃升至37.23%。lbm的变化最为极端：基础配置下仅有约29万次回写更新，启用偏移融合后立即数偏移更新达828万次（增幅2718%），对应的覆盖率从79.72%提升至95.34%，表项几乎在整个测量期间持续有效。相比之下，mcf的总更新变化仅为3.60%，立即数偏移更新仅381万次，反映了该程序以指针追踪为主的访存模式下立即数步进的出现频率较低。

4.4.4　 推测式唤醒分析
　　上文IPC数据显示，从不扩展推测式唤醒到完整方案，综合20个程序提升了0.60%（从2.25%到2.85%）。本节通过自定义硬件性能计数器采集的推测式唤醒数据，定量分析这一扩展的效果和风险。
　　数据中可以得出以下关键结论：
　　1）在最终方案中，重试路径是推测式唤醒的主要来源。重试路径平均贡献了68.17%的推测式唤醒次数，这意味着在完整方案中，超过六成的装入指令的推测式唤醒事件来自被加速的重试执行路径。部分程序的比例更高：lbm（99.99%）、leslie3d（94.66%）、h264ref（82.06%）、cactuBSSN（81.18%）和dealII（80.62%）的比例尤为突出，说明这些程序中绝大多数推测式唤醒事件都发生在Tracing Map加速的装入指令上。这一数据有力地证明了将推测式唤醒扩展到重试路径的必要性。若不进行此扩展，这些绕过发射队列装入指令的依赖指令将无法被提前调度，本文方案缩短装入指令延迟的收益也无法传递给依赖链下游。
　　2）重试路径的唤醒准确率优于正常路径。重试路径的平均失败率为43.00%，显著低于正常路径的70.80%。在20个程序中，18个程序的重试路径失败率低于正常路径（仅leela和lbm两个程序例外）。这一结果的可能原因在于：加速的装入指令一般有着较好的空间局部性（相同基地址寄存器），其数据高速缓存的命中率往往会高于通过正常流水线计算的装入指令，因此推测式唤醒的成功率更高。leela的两条路径失败率接近（30.86%对28.82%），而lbm的两条路径的失败率均趋近100%，情况较为特殊。
　　3）整体推测式唤醒失败率分析。完整方案的整体推测式唤醒失败率平均为51.60%。这一比率虽然较高，但推测式唤醒的代价仅是被唤醒指令的重新调度，不涉及流水线回滚；而推测式唤醒成功时带来的依赖链延迟缩减收益是显著的。因此即使存在一定的失败率，推测式唤醒仍然是对IPC有净正收益的优化策略。由于重试路径的引入降低了加权平均失败率（从正常路径的70.80%拉低到整体的51.60%），推测式唤醒扩展实际上改善了整体唤醒质量。
图4.6　最终方案下推测式唤醒相关参数的比例
　　在所有的基准程序中，blender的表现尤为突出：重试路径占比58.93%，但其失败率仅为19.10%，远低于正常路径的49.57%，说明Tracing Map为其3D渲染中的规则的数组访存提供了高质量的地址预测，使得依赖指令可以以高可信度提前调度。相比之下，lbm 虽然重试路径占比极高，但其失败率也非常高，原因可能在于 lbm 的访存特性使得推测式唤醒失败的概率较大；但由上文分析可知，推测式唤醒不涉及回滚，使得推测式唤醒的失败带来的额外损失较低（IPC 几乎不变化）。
4.4.5　 访存子系统影响分析
　　本文方案改变了装入指令的执行路径，使得装入指令访问存储子系统的顺序产生了变化，对数据转换旁视缓冲器和数据高速缓存均产生了间接影响。
1） 数据转换旁视缓冲器的影响。
　　图4.7和图4.8展示了完整方案相对于基线的数据转换旁视缓冲器的缺失率和访问次数的变化情况：
图4.7　数据转换旁视缓冲器缺失率变化情况
　　所有20个程序的数据转换旁视缓冲器的缺失次数均有所下降，这是本文方案的一个重要间接收益。缺失次数平均下降了10.40%，其中blender的降幅最大（−25.62%），dealII次之（−23.21%）。一个可能的原因：加速的装入指令多来自循环体内对连续地址空间的访问，这些装入指令访问的虚拟页面高度集中。当这些高频装入指令提前进入装入-存储部件时，整个范围的装入指令减少了对数据转换旁视缓冲器表项的占用时间，使其有效容量得到释放，从而降低了整体缺失率。
图4.8　数据转换旁视缓冲器访问次数变化情况
　　缺失率的降低还进一步带动了数据转换旁视缓冲器访问次数的下降：访问次数平均下降了3.16%。这是因为在处理器中，每次数据转换旁视缓冲器缺失都会触发页表遍历，遍历完成后装入指令需要再次访问数据转换旁视缓冲器以完成地址翻译，因此一次缺失事件实际上对应了至少两次数据转换旁视缓冲器访问（首次缺失访问和遍历后的重新访问）。当缺失次数减少时，这些因缺失而产生的重复访问也随之消除，访问总次数因此下降。以blender_r为例，其缺失次数下降了25.62%，访问次数对应下降了4.20%；dealII的缺失次数下降了23.21%，访问次数下降了9.34%。访问次数的降幅小于缺失次数的降幅，这是由于缺失引发的重复访问仅占总访问次数的一部分，但这一效应仍然有利于减轻数据转换旁视缓冲器的访问压力。
图4.9　二级数据转换旁视缓冲器未命中率变化情况
　　尽管一级数据转换旁视缓冲器缺失率普遍下降，但部分程序的二级数据转换旁视缓冲器缺失次数出现了些许上升。
　　二级数据转换旁视缓冲器缺失次数上升的可能原因是：部分装入指令的延迟时间缩短，改变了程序原有的数据转换旁视缓冲器的访问时序。在基线配置中装入指令按照正常流水线顺序执行，数据转换旁视缓冲器访问在时间上可能较为分散；而在加速后，多条装入指令可能在更短的时间窗口内集中到达数据转换旁视缓冲器，当一级数据转换旁视缓冲器缺失后级联访问二级数据转换旁视缓冲器时，集中的访问压力可能导致二级数据转换旁视缓冲器中的页表项被更频繁地替换，从而增加了其未命中率。不过，二级数据转换旁视缓冲器缺失的绝对增幅较小（多数程序在1%至3%之间），总体上这一副作用不太会构成性能瓶颈。

4.4.6　 硬件资源开销分析
　　首先进行理论开销分析。Tracing Map方案中，主要新增了一个Tracing Map表。该表的表项包含1 bit的有效位、1 bit的等待位、6 bit的等待序号以及40bit基地址字段，一个条目的存储开销为48 bit。一共32个条目，故在该方案中寄存器的存储开销为1536 bit；立即数偏移融合功能由于复用了基地址字段，没有增加存储开销；SAB功能中一个条目内有效位占1bit、存储队列序号占4bit、移位寄存器的高位地址占38bit，一个条目占43 bit。在本设计中采用了4级的移位寄存器，且发射宽度为2，故存储开销为344 bit；推测式唤醒拓展不额外使用寄存器。总计新增寄存器为1880 bit，即235 Byte的寄存器开销。该开销不到 BOOM V3 MediumBoom 配置中整数寄存器堆容量（640 Byte）的 37%，是轻量级的微架构扩展。
　　实际运行中，Vivado软件的资源利用报告给出了具体的硬件开销情况。这其中，LUT（Look-Up Table）资源可以视作逻辑的复杂度表现，FF（Flip-Flop）资源可以视作寄存器使用量的表现。经统计，基准BOOM V3处理器的LUT资源使用量为172275，FF资源使用量为95827；Tracing Map方案的LUT使用量为178082，FF资源使用量为98329；立即数偏移融合方案的LUT资源使用量为186583，FF资源使用量为98436；SAB方案的LUT资源使用量为188244，FF资源使用量为98819；最终方案的LUT资源使用量为189309，FF资源使用量为98856。
4.5　 本章小结
　　本章从功能验证和性能评测两个维度对本文方案进行了系统性的实验评估。在功能验证方面，本文方案在 ISA 合规测试、裸机基准程序、riscv-pk 代理内核及 OpenSBI + Linux的完整操作系统启动等多层次测试中均表现正确，未引入任何功能回归。在性能评测方面，基于 FPGA上的实际运行结果和 SimPoint 采样方法论，对 SPEC CPU 2006 和 SPEC CPU 2017 各10个基准程序在五种递进的配置下的性能数据进行了全面分析。完整方案在20个程序上实现了2.85%的IPC几何平均提升。立即数偏移融合模块将Tracing Map的总体平均覆盖率从27.29%提升至44.47%。SAB 在冲突密集型程序中有效抑制了内存序异常并避免了性能回归。访存子系统分析表明数据转换旁视缓冲器缺失率普遍下降，数据高速缓存的缺失率保持稳定。硬件资源分析表明本文方案的资源开销在可接受范围内，未对处理器带来较大的硬件开销。
　　	
　　	
第五章　 总结与展望
5.1　 本文工作总结
　　装入指令的执行延迟是制约超标量乱序处理器单线程性能的关键瓶颈。在传统的乱序执行流程中，装入指令必须在发射队列中等待基址寄存器操作数就绪，经过发射仲裁、寄存器读取、地址生成、虚实地址转换和高速缓存访问等多个流水级后才能完成数据写回，其中发射队列排队延迟是常被忽视但影响显著的因素。本文围绕“消除装入指令的发射队列排队延迟”这一目标，基于开源 RISC-V 超标量乱序处理器 BOOM V3，设计并实现了一种跟踪基址的装入延迟隐藏机制，完成了从设计、实现到验证评测的完整工作。
　　本文首先系统回顾了与本文相关的工作，主要为装入延迟优化相关的代表性工作。在装入地址预测方向，回顾了该领域相关技术的演进，并与本文方案在索引方式、预测性质、覆盖范围等方面进行了深入对比；在存储相关预测方向，回顾了通过控制流预测存储相关的方案，阐述了存储相关预测对缓解存储-装入内存序违例的重要性；在投机调度方向，回顾了重放机制的技术权衡和差异化投机策略，阐明了推测式唤醒扩展至重试路径的必要性。
　　本文利用程序中基址寄存器值的时效性局部性，基于BOOM V3（SonicBOOM）处理器提出了一种跟踪基址的装入延迟隐藏机制。通过对 BOOM V3 流水线架构和装入执行流程的系统分析，本文识别出三项关键架构特征：重试路径可作为零成本的存储子系统的接入点、存储-装入冲突是装入指令提前执行的主要风险以及推测式唤醒机制重试路径扩展。并据此设计了由四个递进协作子模块组成的完整方案：Tracing Map核心模块以逻辑寄存器号为索引缓存精确基址值，在译码阶段完成地址预测与发射队列旁路；立即数偏移融合将自增偏移累积到缓存基址字段中，覆盖循环步进模式并支持非自增的立即数加减和寄存器移动指令的传播；SAB冲突预检测模块在分派阶段对提前解析出地址的装入指令进行存储-装入的地址级冲突预判，从源头控制内存序违例风险；推测式唤醒扩展将重试路径纳入唤醒触发条件，使延迟缩短收益沿依赖链传播。全部方案基于Chisel实现，新增寄存器开销约235字节。
　　方案在 Verilator 仿真和 FPGA硬件平台上通过了多层次功能验证，包括 ISA 合规测试、裸机基准程序、riscv-pk 代理内核及 OpenSBI + Linux 操作系统启动，确认了功能正确性；基于 SimPoint 采样方法论对10个 SPEC CPU 2006 和10个SPEC CPU 2017基准程序的性能评测表明：完整方案实现了 2.85% 的 IPC 几何平均提升。立即数偏移融合将覆盖率从 27.29%提升至44.47%；SAB 在冲突密集型程序中有效抑制了微异常并扭转了性能回归；推测式唤醒拓展进一步增加了性能，证实了该扩展是较低风险且较高收益的优化策略。
5.2　 未来工作展望
　　尽管本文的 Tracing Map 方案在 BOOM V3 MediumBoom 配置上取得了一定的性能收益，但仍存在多个值得进一步探索的研究方向：
　　1）SAB 冲突检测能力的增强。第四章的实验分析显示，在个别场景下SAB的效果并不显著。未来可以探索自适应的 SAB 设计，根据运行时的微异常反馈动态调整检测窗口深度或冲突判定策略；也可以考虑引入基于控制流的辅助冲突历史表，与 SAB 的地址级检测互补，形成混合冲突预测机制。
　　2）与其他装入延迟优化技术的协同。本方案主要针对一级高速缓存命中的装入指令缩短其发射队列排队延迟。对于二级或三级高速缓存缺失的装入指令，可以使用硬件预取等技术进行优化。未来可以探索本方案与预取器的联合优化，例如利用预测的地址流驱动数据预取，在Tracing Map命中的装入指令完成缓存访问的同时为后续装入指令启动预取，从而同时覆盖一级高速缓存命中和高速缓存缺失两种场景。
　　3）同时多线程环境下的扩展。当前方案仅考虑单线程场景。然而，在同时多线程（SMT）环境下，多个线程共享同一物理核心的 Tracing Map 表结构，不同线程的逻辑寄存器号会产生冲突。未来可以探索线程间的 Tracing Map 资源分配策略，例如静态分区、动态共享或按线程标识扩展索引等方案，使 Tracing Map 在多线程负载下仍能有效工作。
